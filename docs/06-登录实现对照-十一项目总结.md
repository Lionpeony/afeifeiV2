## 2. 归纳：登录实现的四种架构

| 架构 | 代表 | 优点 | 代价 | 我们适用吗 |
|---|---|---|---|---|
| **A. 本地拉起 API 服务**（主进程内嵌 node 服务，每源一个） | Folia（NCM-Enhanced + qq-music-api 包）、Mineradio（server.js）、SPlayer（外部部署 NCM） | 协议细节全在服务里，桌面主进程天然能持 MQTT 长连接；**加源 = 加一个服务模块** | 服务代码体积；NCM 包 380 个接口的面收敛问题（我们已用白名单解决） | ✅ **已采用**（NCM 内嵌），QQ/酷狗/汽水延续 |
| **B. 渲染层直连**（cookie 放 localStorage） | YesPlayMusic（部分）、多数 Web 版 | 简单 | CORS 依赖代理、cookie 暴露在渲染层（00 §11 不允许） | ❌ 违反我们的安全模型 |
| **C. 插件自管登录**（插件协议带 getLoginUrl/getLoginStatus） | MusicFree | 本体零耦合，源无限扩展 | 登录体验参差（各插件各写各的）、插件质量不齐 | ⬜ 我们的 M5 用户源沙箱已是同思路，且沙箱隔离更强 |
| **D. 每源独立 session 分区 + 真实页面** | Mineradio（`persist:mineradio-qqmusic-login`…） | cookie 隔离防串号、持久化免费（Chromium 自带）、真实页面抗风控 | 依赖页面 DOM（改版要修） | ✅ 值得立刻借——我们当前所有源共用默认 session，**已存在跨源串号风险**（QQ 与网易云若未来有同域 cookie 会互相污染） |

## 5. 对我们架构的三条直接启示（ Mineradio 验证过的）

1. **session 分区**：`session.fromPartition("persist:<source>-login")` 给每个可登录源独立分区——登录窗口、`net.fetch`、cookie 全在该分区内，跨源永不串。
2. **IPC 信任边界**：登录态读取要校验"主文档 URL"（Mineradio 的做法），防用户源沙箱里的脚本借渲染层身份读登录 cookie——我们的用户源沙箱目前拿不到 session，但加一道校验更稳。
3. **凭证导出通道**（per-provider cookie 文件 + 环境变量覆盖）：我们 M6.6 的备份已排除凭据，Mineradio 的"显式导出"是更好的折中（用户可迁移登录态），列为可选项。
