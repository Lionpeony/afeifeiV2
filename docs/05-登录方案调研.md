# 05 · 登录方案调研：网易云 / QQ 音乐 / 酷狗 / 汽水

> **性质**：2026-11-03 的专项调研（应"看看各家播放器的登录怎么做的、判断可抄袭代码的优先级"）。
> **结论先行**：四个源里三个有 **MIT** 的现成实现可合法抄；QQ 与酷狗各有一个"类 NCM"的 API 包；汽水有 MIT 参考实现。
> **许可基调**：本项目 AGPL-3.0-only——MIT/Apache 代码可并入（登记 `THIRD-PARTY-NOTICES.md`）；GPL-3.0-only 代码按 GPLv3 §13 可组合进 AGPL 作品；**无 license 的代码一律只看不抄**。

## 1. 网易云音乐 ✅（已完成，作对照基线）

- **协议**：`interface3.music.163.com` unikey 三件套——`login/qr/key` → `login/qr/create`（二维码）→ `login/qr/check` 轮询（800 待扫 / 801 已扫 / 802 待确认 / 803 成功）；备选手机号 `captcha_sent` + `login_cellphone`。
- **我们的实现**：`NeteaseCloudMusicApi`（npm，MIT）内嵌主进程，`LoginDialog` 应用内二维码（`03` 2026-11-02 条目）。
- **各播放器**：Folia（`NeteaseCloudMusicApiEnhanced`，桌面版启动时**先刷新 xeapi 公钥与匿名令牌再开窗**——这是它启动要 10 秒的原因之一，我们没有这一步，登录态过期频率可能更高，列入观察项）；SPlayer/YesPlayMusic 同用 NCM 系。
- **对照结论**：无需动作。

## 2. QQ 音乐 🟡（P1）

### 2.1 协议现实（我们已踩过）

| 通道 | 协议 | 风控现实 |
|---|---|---|
| ptlogin 扫码（`ptqrshow`/`ptqrlogin`） | HTTP + hash33(qrsig) 轮询 | **TLS 指纹风控**：node 与 Electron `net.fetch` 手写请求全 403（2026-11-03 实测）→ 我们改用隐藏页方案登录可行，但播放地址走不动 |
| QQ 音乐 App 扫码 | **MQTT over WSS**：注册设备 → 建二维码 → 订阅 qrcodeID → 上游推 `scanned`/`cookies` → 凭证交换 | 必须**常驻进程持有长连线**（clean session + unicast，断线即死局）——正是桌面主进程的强项 |
| 微信扫码 | 类似，走服务端通道 | Folia 在 Vercel 上只支持微信（serverless 持不了连接） |
| QIMEI | 设备身份，需跨重启保留 | 协议要求 QIMEI 引导与后续调用同设备身份 |

### 2.2 谁实现了、什么许可

| 项目 | 许可 | 形态 | 可抄性 |
|---|---|---|---|
| **`@yakult-green-tea/qq-music-api`（3.3.5）** | **MIT** | npm 包，**可嵌入 Electron 主进程**（导出 server + `configureAuthSessionRepository` 注入加密会话仓库） | **可直接用**。Folia 生产在用（桌面版 `qqBackend.start()`；手机 QQ 扫码要求 ≥3.3.3） |
| senchenjian/qq-music-api（fork Rain120） | 待核实 | Koa2 + TS 独立服务，含扫码 | 若 MIT 可作备选 |
| jsosso/qq-music-api（我们误装的 1.1.2） | **无 license** | 独立服务，无登录路由 | 只看，已从依赖移除计划 |
| Folia | AGPL-3.0 | 桌面版内置 `qqBackend.start()` + QIMEI 卷 + 登录态存系统安全存储 | 借做法（同 AGPL 可抄，但其集成面太大） |

### 2.3 建议实现（P1，1–2 天）

1. `package.json`：移除 `qq-music-api@1.1.2`（无 license）→ 换 `@yakult-green-tea/qq-music-api`（MIT，`gate:` 无关、白名单更新 + `docs/02` 登记）
2. `main/net/qqSession.ts` 重写：主进程 `require("@yakult-green-tea/qq-music-api")` 拉起服务（Folia 的 `qqApiStartup.cjs` 同款做法），扫码通道/登录态/播放地址全部由它内部完成
3. 渲染层契约不变：`startLogin("qq")`/`pollLogin("qq")`/`getUrl` 只是底层换实现——`LoginDialog` 的应用内二维码体验保留（二维码图由服务出）
4. 登录态持久化：用它的会话仓库接口接我们的 KV（或按其默认内存 + 重启重扫，先跑通再说）
5. **替换后旧的隐藏页方案删除**（保持单一实现，不留第二真相）

**风险**：该包非官方（README 自己声明"社区维护，与腾讯无隶属"）；QIMEI/凭证寿命等行为由它内部处理，我们失去对细节的可见性——但换来的可用性远超手写。回退路径：隐藏页登录方案在 git 历史里（`b80b6be`）。

## 3. 酷狗（P2）

- **协议现状**：酷狗概念版（lite）扫码登录最成熟；开源圈的事实标准是 **KuGouMusicApi**（MakcRe，100+ 模块，含登录/二维码/签名工具；gitcode 有镜像 `gh_mirrors/ku/KuGouMusicApi`）。npm 无同名包（404），要用需从 GitHub 拉源码——**license 未核实，抄码前必须核**。
- **其它参考**：a1sunyuwen/kugou-api（Vercel 部署版，登录/刷新/dfid/歌单）；KuGouWebPlayer（概念版扫码）；MusicFreePluginsHub 的酷狗插件（MusicFree 插件形态，JS 沙箱——与我们的用户源沙箱同构，但那个插件是匿名接口为主）。
- **建议实现**：2–3 天——确认 KuGouMusicApi 许可 → 若 MIT：本地拉起 + 契约壳（同 QQ 的模式，第二家走通后是**复制粘贴级**工作）；若非 MIT：只抄它的**请求签名算法**（签名是函数级事实，许可约束弱于结构）。
- **判据**：扫码登录 → 搜歌 → 播放 → 歌单列表；加源只动 `capability/sources/` + 注册一行。

## 4. 汽水（P3）

- **协议现状**：`api.qishui.com/luna/pc/*`；请求带 `x-helios`/`x-medusa` 签名头 + DEVICE_ID；**有 MIT 的完整参考实现**：
  - **`guowenye/qishui-api`（MIT）**：汽水原生接口 + **扫码登录** + 歌词 + 播放字段；有 Node 参考实现（`src/qishuiClient.js`）；MeloX-Android 已按它核对过协议（`QISHUI.md` 是现成的字段核对记录）。
  - 520Qiuyu/qishuiMusicAnalysis：走**抓包**拿 DEVICE_ID/COOKIE/x-helios/x-medusa（说明部分部署形态依赖真机凭证——qishui-api 是否内置设备注册需读源确认，这是 P3 的最大变数）。
  - `ly-music-source`（npm，**GPL-3.0-only**）：Qishui/Soda/Luna PC API——GPL 代码按 GPLv3 §13 可并入 AGPL 项目，但优先用 MIT 的 qishui-api。
- **建议实现**：3–4 天——读 qishui-api 的扫码与签名部分 → 抄接口序列进 `main/net/qishuiClient.ts`（**MIT 代码并入需逐文件登记 NOTICES + 保留版权头**）→ 契约壳 + UI。
- **风险**：字节系签名算法随版本变；64 位 ID 一律按字符串处理（MeloX 踩过的坑）；汽水曲库以短视频热歌为主，优先级自然靠后。
