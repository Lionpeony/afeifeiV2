### 1.2 三个问题

**问题一：播放器在本质上是干什么的？**

剥掉所有功能，它只做四件事：

1. **持有**一批音频（本地或远端）
2. **决定**下一首放什么
3. **渲染**声音
4. **显示**一些东西

在线音源、歌词、可视化、歌单、下载——全部是 ① 或 ④ 的延伸。**所以设计的第一优先级是把这四件事各自做到无歧义，而不是先做功能。**

**问题二：这种东西最容易烂在哪？**

不是性能，不是功能不够，而是**同一件事有多个真相**：

| 现象 | 本质 |
|---|---|
| 进度条和歌词不同步 | 时间有两个来源 |
| 从搜索里播一首，专辑队列没了 | 队列与来源混成一个东西 |
| 加了新音源，收藏按钮点了报错 | 能力靠"试"而不是靠"声明" |
| 特效一多就掉帧 | 五个动画循环抢一个主线程 |
| 换个主题要改 20 个组件 | 颜色没有唯一来源 |
| 重构一次烂一次 | 约束没有被执行，只被写在文档里 |

**所有"烂"，都是"同一件事的真相不唯一"。**

**问题三：那把真相收成唯一的呢？**

这就是全部设计。把六类真相各收成唯一：

| 真相 | 唯一化成什么 | 不变式 |
|---|---|---|
| 现在播到哪一秒 | 一个时钟 | **I1 单一时间源** |
| 应用现在是什么状态 | 一个 store，一个写者 | **I2 单一事实源** |
| 声音怎么出来的 | 一张音频图 | **I3 单一音频图** |
| 某个东西能做什么 | 一份声明 | **I4 能力先声明后使用** |
| 能花多少资源 | 一组预算 | **I5 资源有预算** |
| 这个动作是谁发起的 | 一条 intent | （由 I2 派生） |

### 1.3 五条不变式（本文的全部约束）

| # | 不变式 | 一句话 | 违反的典型症状 | 怎么强制 |
|---|---|---|---|---|
| **I1** | 单一时间源 | 播放位置只有一个来源，所有消费方读它 | 歌词、进度条、频谱三套时间，越播越偏 | lint：`src/` 里禁 `setInterval` / `Date.now()` 做动画；只有一个模块能读 `audio.currentTime` |
| **I2** | 单一事实源 | 一个 store，每个域一个写者，UI 只发 intent | 谁改了状态说不清；改 A 坏 B | lint：一个域出现第二个写者即失败；组件里禁 import store 的写方法 |
| **I3** | 单一音频图 | 全进程一个 AudioContext，效果是可插拔节点 | 两处 `new AudioContext`，音量/EQ 互相覆盖 | 测试：`grep -c "new AudioContext"` = 1 |
| **I4** | 能力先声明后使用 | 任何能力必须先声明，UI 按声明渲染 | "点了才报错"；新源上线要改界面 | 契约测试：声明表 ↔ 实现方法必须一一对应 |
| **I5** | 资源有预算 | 内存/帧/网/盘都有上限，超了按序降级 | 播两小时内存 1.5G；特效一开就掉帧 | 性能脚本进 CI；降级表写死顺序 |

**这五条不是口号，每一条都有一个能在 CI 里变红的检查。** 这是本文与"架构 PPT"的唯一区别。

## 2. 五环 + 一个端口：依赖只能向内，出站只能走一个门

普通分层（UI / 业务 / 数据）的问题是：业务层偷偷 import 了 UI 的常量，数据层偷偷做了业务判断。**环模型解决它：依赖只能向内，内层永远不知道外层存在。**

但**宿主（主进程）不是外层容器**——它是**另一个进程**。把它画成"包在最外面的一圈"是个常见错误：它既不在环里，也不是被依赖的方向。所以本文的模型是 **五环（应用内部）+ 一个端口（出站）+ 一个环境（宿主）**。

```
        环境（Ring 之外）
  ┌──────────────────────────────┐
  │ Electron 主进程：窗口 / 协议 │
  │ / fs / net / 托盘 / 快捷键   │
  └──────────────┬───────────────┘
                 │  ↑ 只经 contracts + preload 这一个端口
                 │  出站调用必须经过它，不许旁路
┌────────────────┴───────────────────────────────┐
│ 渲染进程（应用本体）                            │
│                                                │
│   ┌─────────────────────────────────────────┐  │
│   │ Ring 4  表皮  React 组件 + token + 合成器│  │ ← 只读投影，只发 intent
│   │  ┌───────────────────────────────────┐  │  │
│   │  │ Ring 3  投影  selector（纯函数）   │  │  │
│   │  │  ┌─────────────────────────────┐  │  │  │
│   │  │  │ Ring 2  能力  provider/注册  │  │  │  │
│   │  │  │  ┌───────────────────────┐  │  │  │  │
│   │  │  │  │ Ring 1  领域  库/歌单  │  │  │  │  │
│   │  │  │  │  ┌─────────────────┐  │  │  │  │  │
│   │  │  │  │  │Ring 0 内核       │  │  │  │  │  │
│   │  │  │  │  │时钟/队列/播放器  │  │  │  │  │  │
│   │  │  │  │  └─────────────────┘  │  │  │  │  │
│   │  │  │  └───────────────────────┘  │  │  │  │
│   │  │  └─────────────────────────────┘  │  │  │
│   │  └───────────────────────────────────┘  │  │

└────────────────────────────────────────────────┘
```

| 环 | 名字 | 里面有什么 | 允许 import | 绝不允许 | 对应目录（§12） |
|---|---|---|---|---|---|
| **0** | 内核 | 时钟、队列、播放器状态机、store | 只 import 类型 | 碰 DOM、碰 IPC、碰 React | `renderer/kernel/` |
| **1** | 领域 | 曲库规则、歌单、收藏、历史、去重 | 环 0 | 碰 React、碰 IPC 具体实现 | `renderer/domain/` |
| **2** | 能力 | 音源、歌词解析、舞台、主题的契约与注册 | 环 0/1 + `contracts/` | 碰 UI 组件、硬编码平台名 | `renderer/capability/` |
| **3** | 投影 | selector：把状态算成视图模型 | 环 0/1/2 的只读数据 | 写状态、发请求 | `renderer/projection/` |
| **4** | 表皮 | React 组件、CSS token、合成器 | 环 3 + 环 0 的 intent | 直接调用环 1/2、直接 fetch/IPC | `renderer/ui/` |
| — | **端口** | `contracts/`（纯类型）+ `preload/`（具名方法） | — | 任何一侧都不许绕过它 | `contracts/`、`preload/` |
| — | **环境** | 窗口、协议、托盘、快捷键、文件、网络 | Node / Electron | **任何业务判断** | `main/` |

**"向外"的三个后果（这是环模型唯一的破例，必须写清楚）**：

1. **出站只能走端口**：环 0–4 都不许直接 `ipcRenderer`，只能调 `contracts/` 里声明的服务；端口后面才是 `main/`。
2. **端口是窄的**：端口上每加一个方法，都要问"能不能用已有的三个方法组合出来"。
3. **环境不知道应用存在**：`main/` 里不许 import 任何 `renderer/` 的东西（连类型也不行，类型只在 `contracts/`）。

> 这样"依赖只能向内"依然成立：**环之间的箭头永远向内，向外的只有"端口"这一条线**。把主进程画成外圈会让人误以为"内层可以随便依赖主进程"，那正是 Electron 应用失控的开始。

### 2.1 为什么宿主（主进程）里不能有业务

大多数 Electron 应用把"扫描曲库、判断去重、决定缓存策略"写在主进程，理由是"那里能读文件"。**这是把两件事混了**：

- **读文件**是系统调用（宿主的事）
- **要不要索引、怎么合并、什么算重复**是业务（领域的事）

分开的好处很硬：

1. 业务能被单测（不需要起 Electron）
2. 换壳（Electron → 别的）只改"环境"与端口实现（`main/` + `preload/`），环 0–4 一行不动
3. 主进程代码量压到最低，攻击面自然小

**代价**：多一次 IPC。解法是**批量**——一次 `fs.readTags(paths[200])`，而不是循环 200 次。实测 5000 首标签读取的 IPC 开销可以忽略，而主进程瘦下来是永久的。

> 唯一的例外：**标签解析**放在宿主（它是"读文件内容"的延伸，一个纯函数库）。但"要不要重解析"由领域决定。

## 3. 时间模型（I1）

播放器所有"看起来不对"的问题，一半出在时间。所以时间要单独设计。

### 3.1 定义

```ts
export interface Clock {
  /** 当前播放位置（ms）。播放中插值，暂停时冻结 */
  now(): number;
  /** 订阅（帧级）。回调收到的是同一个 t，不是各自算的 */
  onTick(cb: (t: number) => void): () => void;
  /** 音频元素的原生事件（seek/ended/ratechange），唯一被允许读 audio.currentTime 的地方 */
  attach(el: HTMLAudioElement): void;
}
```

### 3.2 三条规则

1. **只有 `clock` 能读 `audio.currentTime`。** 其他任何模块（歌词、进度条、频谱、舞台）只准 `clock.now()`。
2. **只有 `clock.seek(ms)` 能写 `currentTime`。** 进度条拖动、`←/→`、跳到歌词行、Scheme URL 的起播位置，全部走这一个口（UI 只发 intent）。**禁止任何组件直接 `audio.currentTime = x`。**
3. **播放中插值**：`now = lastKnownTime + (performance.now() - lastKnownAt) * rate`。这样界面是 60fps 平滑的，而不是等 `timeupdate` 事件（那个 4Hz，肉眼可见的顿）。
4. **漂移守卫**：每次 `timeupdate`（或 rAF 每 500ms）比对一次，若 `|插值 - 真实| > 80ms` → **立刻吸附到真实值**，不追平。追平会看到歌词"赶进度"，比跳一下更丑。
5. **crossfade 期间 clock 只跟"出场那一路"**：两首同时响时，位置属于**即将结束的旧曲**；到切点（新曲成为主轨）一次性把 `t` 归零到新曲，**不交叉插值**——交叉插值会让进度条先倒退再前进。切点由 `fade` stage 通知 `player`，`player` 再调 `clock.rebind(newElement)`。

> 第 5 条是"单一时间源"唯一的例外，也是它必须被写死的地方：**双音轨 ≠ 双时钟。**

### 3.3 为什么这很重要

| 常见做法 | 后果 |
|---|---|
| 各模块自己 `setInterval(50)` | 三个定时器不同步，歌词比进度条快 200ms |
| 只用 `timeupdate` 事件 | 4Hz 更新，逐字歌词抖 |
| 用 `requestAnimationFrame` 各算各的 | 一帧内多个时间快照，同一个 tick 里两个组件读到不同 t |

**我们的做法**：一个 rAF 循环由**合成器**拥有（§9），每帧取一次 `clock.now()`，把这个 `t` **分发**给所有订阅者。一帧内所有消费者拿到的时间**完全相同**。

```ts
// 合成器：全应用唯一 rAF
function frame(ts: number) {
  const t = clock.now();                 // ← 一帧只取一次
  for (const sub of subscribers) sub(t); // ← 同一个 t 分发给所有人
  requestAnimationFrame(frame);
}
```

## 4. 队列模型（I2 的核心难点）

**队列是播放器最容易做错的东西。** 错法有两种：

| 错法 | 症状 |
|---|---|
| 一个 `list` + 一个 `index`，所有入口都往里塞 | 从搜索播一首，专辑队列被覆盖；"下一首播放"把队列顺序改乱 |
| 把 shuffle 实现成"打乱数组" | 关掉 shuffle，顺序回不去了 |

### 4.1 三个东西必须分开

```ts
interface Queue {
  items: TrackRef[];        // 将要播放的顺序
  cursor: number;           // 当前播放的位置下标
}
interface Context {
  kind: "album" | "playlist" | "search" | "radio" | "single";
  id?: string;
  label: string;            // 界面上显示"正在播放：XXX"
}
interface History {
  played: TrackRef[];       // 环形缓冲，容量 200
}
```

| 动作 | 对 Queue | 对 Context | 对 History |
|---|---|---|---|
| 从专辑播 | **整体替换** | 替换 | 清空？不，保留 |
| 从搜索播一首 | 整体替换为单曲 | 替换 | 保留 |
| 下一首播放 | 插入 `cursor+1` | 不变 | 不变 |
| 稍后播放 | 追加末尾 | 不变 | 不变 |
| 上一首 | `cursor-1`（播过 3s 则先回开头） | 不变 | 写入 |
| 切 shuffle | **不变**（见 §4.2） | 不变 | 不变 |

> "播过 3 秒按上一首回开头，否则回上一首"——这是所有主流播放器的默认直觉，必须实现，否则用户会以为按钮坏了。

### 4.2 shuffle 是投影，不是变异

**关键决定**：shuffle 不改变 `items`，而是产生一个**派生顺序**。

```ts
/** 纯函数：由 queueId 与 seed 决定，确定且可复现 */
function orderOf(queue: Queue, mode: ShuffleMode, seed: number): number[];
```

- 开 shuffle → 用 `seed` 生成一个置换（保证**当前曲目是置换的第 0 位**）
- 关 shuffle → 直接返回 `0..n-1`，**顺序原样回来**
- 重启应用 → `seed` 持久化，**顺序不变**（用户会记得"下一首是哪首"）
- **光标永远指向"曲目"，不是"位置"**：用户在 shuffle 下点了列表第 7 行，先算出该曲目在置换里的下标再移 `cursor`——否则"点了 A 却在播 B"

这个决定让"切 shuffle 后队列乱了"这类 bug **在结构上不可能发生**。

### 4.3 队列持久化

`userData/queue.json`：`{ items, cursor, context, mode, seed, positionMs }`，**写盘节流 1s**，退出时立刻刷。崩溃后重启恢复：位置回退到最近一次刷盘点。

## 5. 音频模型（I3）

### 5.1 图结构

```
<audio>  ──MediaElementSource──▶  fade ──▶ preamp ──▶ eq ──▶ analyser ──▶ destination
   ▲                                ▲
   │                                └── crossfade 时第二路 <audio> 汇入这里
   └── 唯一被允许读写 currentTime 的元素
```

| 节点 | 职责 | 参数 |
|---|---|---|
| `fade` | 切歌淡入淡出、crossfade 增益交叉 | 切歌 220ms / 暂停 120ms / crossfade 0·3·6s |
| `preamp` | ReplayGain / 手动增益 | ±12dB |
| `eq` | 6 段 Biquad | ±12dB |
| `analyser` | 供频谱与节拍 | `fftSize 2048` |

**Stage 协议**：

```ts
interface AudioStage {
  id: "fade" | "preamp" | "eq" | "analyser";
  create(ctx: AudioContext): { input: AudioNode; output: AudioNode; dispose(): void };
  bypass(on: boolean): void;   // 可旁路，不可运行中销毁
}
```

### 5.2 三条规则

1. **全进程只有一个 `AudioContext`**，由 `pipeline` 拥有。别处 `new AudioContext()` 一律 lint 失败。
2. **效果是节点，不是分支**。想加"空间感"就加一个 stage，不许在播放逻辑里写 `if (effectEnabled) ...`。
3. **`analyser` 允许返回 `null`**（Web Audio 不可用时）。舞台必须能纯几何降级，**不许画假波形**——假数据比没数据更坏，它会让用户以为"这歌没低频"。

### 5.3 gapless 与 crossfade 的实现边界

| 能力 | 实现 | 不能做什么 |
|---|---|---|
| 切歌淡入淡出 | 单元素 + 增益包络 | — |
| crossfade | 双 `<audio>` 交替 + 两条增益曲线交叉 | 不能靠 `MediaSource`（本地文件不值得） |
| 无缝专辑（gapless） | 第二元素预载下一首前 512KB，边界处切换 | 不能承诺"绝对 0 采样缺口"（浏览器不给保证），文案写"近乎无缝" |

> 诚实是设计的一部分：**做不到 100% 的，文案就别写 100%。**

## 6. 数据模型

### 6.1 身份与去重

| 概念 | 定义 | 为什么 |
|---|---|---|
| `TrackId` | `sha1(realpath)` 的前 16 hex | 稳定、短、可做文件名 |
| `dupeKey` | `lower(title) + "\u0000" + lower(artist) + duration±2s` | 用于**建议去重**与**移动识别**，不自动合并曲目（自动合并必然误杀现场版） |
| `sourceKey` | `{ providerId, mediaId }` | 线上曲目**永不**只有 id，必须带来源 |

**规则**：任何跨模块传递的曲目都必须是 `TrackRef = { kind: "local", id } | { kind: "remote", sourceKey }`。**没有第三种形态，也不许只传字符串。**

**移动与重命名（id 会变，这是必须正面处理的问题）**：
路径一变 `realpath` 就变 → `TrackId` 变 → 队列、收藏、歌单里的旧 id 全部指向不存在的曲目。

处理顺序（扫描结束后执行一次）：

1. 找出"索引里有、这次没扫到"的 **消失集** 与"这次新出现"的 **新增集**；
2. 对每一对 `dupeKey` 相同 **且** `size` 相同的组合 → 判定为**同一文件被移动** → 写一条 `remap{oldId,newId}` delta；
3. 队列 / 收藏 / 歌单里的 `TrackId` 在读取时经 remap 表转换（**不改历史数据**，只改解析）；
4. 无法配对的消失曲目 → 标记 `missing`（界面置灰、可一键"重新定位"，**绝不自动删除**）；
5. remap 表本身也会过期：某个 `oldId` 连续 3 次启动都没被引用 → 清掉。

> 为什么不直接用 `dupeKey` 当 id：同名同歌手同长度的歌真实存在（专辑版 / 精选版），**用内容特征当身份会静默合并两首歌**，比"移动后要修"更糟。

### 6.2 索引：快照 + 增量日志（无新依赖）

单文件 JSON 的问题：5000 首改 1 首也要重写 2MB，且写到一半断电就废。

**方案**（借鉴 WAL 思想，但只用一个文件对）：

```
userData/library/
  snapshot.json    全量快照（写时先写 .tmp 再 rename）
  delta.log        增量日志（每行一个操作，追加写）
  snapshot.meta    快照对应的 delta 偏移量
```

启动：读快照 → 重放 `delta.log` 中偏移之后的行 → 内存索引。
达到 **500 条 delta 或 每日首次启动** → 合并成新快照，清空日志。

| 指标 | 值 |
|---|---|
| 5000 首冷读 | < 120ms |
| 单次增量写 | 追加一行，< 1ms |
| 崩溃安全 | 最坏丢最后一行 delta；快照永远完整（rename 原子） |
| 索引版本变更 | `version` 不匹配 → **全量重建**，不写迁移 |

> **为什么不 SQLite**：它需要一个 native 依赖（打包要匹配 ABI），而 5 万首以内 JSON+WAL 足够。把"够用"和"先进"分开——见 §15。

### 6.3 缓存

| 缓存 | 位置 | key | 上限 | 淘汰 |
|---|---|---|---|---|
| 封面缩略图 | `userData/cache/covers/` | `sha1(path+size+mtime)` | 200MB | LRU |
| 节拍分析 | `userData/cache/beats/` | `sha1(id+size+mtime)` | 50MB | LRU |
| 线上地址 | 内存 | `sourceKey+quality` | 5 分钟 TTL | 到期 |

写盘一律 `.tmp` + `rename`；上限检查在**写入后**做（先写成功再淘汰，避免写到一半把自己淘汰了）。

## 7. 能力模型（I4）

### 7.1 只有四个扩展点

**这是刻意的克制**：扩展点每多一个，"能坏的地方"就多一片。

| 扩展点 | 加它的人 | 加完能得到什么 |
|---|---|---|
| **SourceProvider** | 我们或社区 | 多一个音源：搜索/播放/歌词/收藏/歌单 |
| **StageProvider** | 我们 | 多一种播放页视觉 |
| **LyricRenderer** | 我们 | 多一种歌词看法 |
| **ThemePack** | 用户（纯数据） | 换一套皮 |

**其它一律不开放**：不加"通用插件"、不加"脚本钩子"、不加"UI 插槽"。想要第五个扩展点，先证明前面四个做不到。

### 7.2 声明式契约

```ts
interface Capabilities {
  search: boolean; suggest: boolean; playback: boolean;
  lyrics: boolean; wordByWordLyrics: boolean;
  album: boolean; artist: boolean;
  playlistRead: boolean; playlistWrite: boolean;
  likes: boolean | "read" | "write" | "both";   // 能表达"能读不能写"
  daily: boolean; personalFm: boolean; tops: boolean;
  mv: boolean; cloudDisk: boolean;
  auth: "qr" | "cookie" | "oauth" | null;
  multiQuality: boolean; stream: boolean;
  comments: boolean; share: boolean;
}
```

**规则**：

1. UI 只读 `capabilities`，**从不 try/catch 探测**。
2. 声明为 `false` 的能力 → 对应控件**不渲染**（不是置灰，是不存在）。
3. 调用未声明的能力 → 立即抛 `capability-missing`，这是**我们自己的 bug**，不是用户的错。

### 7.3 三级扩展与信任边界

| 级别 | 谁写 | 运行在哪 | 隔离 |
|---|---|---|---|
| 内置 | 我们 | 主进程 | 无（可信） |
| 官方扩展 | 我们 | 主进程 | 无（可信） |
| **用户源** | 社区 | **独立 utilityProcess** | 只注入 `host.*`；无 `fs`/`net`/`require`；单次 8s、内存 128MB、崩溃不影响主进程 |

用户源能做的事**只有 `host.*` 里列的**：

```ts
interface HostApi {
  http(req: { url: string; method?: string; headers?: Record<string,string>; body?: string }): Promise<{ status: number; body: string }>;
  log(level: "info" | "warn", msg: string): void;
  cache: { get(k: string): Promise<string | null>; set(k: string, v: string, ttlMs: number): Promise<void> };
}
```

> 注意 `http` 是**宿主代理**，不是让脚本自己发请求——这样 Cookie、UA、限流、失败分类全部还在我们手里。

### 7.4 歌词：解析一次，渲染器可换

> 歌词是播放器里唯一"数据复杂 + 表现花哨"的东西，所以它必须被切成两半：**解析**与**渲染**。
> 这一刀切不准，就会像多数播放器一样长出三套歌词代码，互相打架。

**两半的分界**：

```
主进程：文本 → LyricDoc（纯数据，无 DOM）      ← 四格式 + 逐字 + 智能重排
渲染层：LyricDoc + clock → DOM                  ← 四个渲染器，可换
```

```ts
interface LyricDoc {
  lines: Array<{
    t: number;                 // 起始 ms
    end: number;               // 结束 ms
    text: string;
    words?: Array<{ t: number; d: number; text: string }>;  // 逐字
  }>;
  /** 解析器自报的问题：时间乱序 / 缺结束时间 / 单字行，供 UI 提示，不静默 */
  issues: Array<"out-of-order" | "missing-end" | "single-word-line">;
}
```

**规则**：

1. **解析在主进程**，产物是纯数据。渲染层拿不到原始文本（也就没法长第二套解析）。
2. **渲染器只吃 `LyricDoc` + `clock`**，**不准自己起 rAF**（时间来自合成器，见 §9.1）。
3. **逐字推进只碰 `transform` / `clip-path`**，禁逐帧改 `width`（会触发布局，逐字歌词必掉帧）。
4. **四个渲染器上限**：`press`（印刷）/ `karaoke`（逐字）/ `minimal`（单行）/ `theatrical`（剧场位移）。加第五个必须先删一个。
5. **解析问题要暴露**：`issues` 非空时，歌词页给一个不打扰的角标——**不静默修正**（静默修正会让用户以为"这歌的歌词就是这样"）。

**智能重排**（解析后、渲染前的一道纯函数）：长句拆行（按标点与字数上限）· 去掉行首标点 · 末行不落单字 · 时间戳单调化。**它必须是纯函数且有单测**，否则每次调都像碰运气。

**桌面歌词窗**（取 LX 的形态）：独立置顶透明窗，**独立 preload（只暴露 3 个方法）**；两种鼠标态 `interactive` / `click-through`，鼠标进入歌词包围盒临时解除穿透，中键锁定。位置与字号持久化。

**验收**：同一首歌切四个渲染器，`lines.length`、首行 `t`、逐字 `t` **逐项相同**（对拍脚本 diff = 0）；切渲染器 ≤ 100ms。

## 8. 投影模型：UI 为什么可以很薄

```ts
// 领域 → 状态（唯一写者）
player.playFrom(context, tracks);      // 只有它能改 playerStore

// 状态 → 视图模型（纯函数，可单测）
export const selectNowPlaying = (s: State): NowPlayingVM => ({ ... });

// 组件：只读投影 + 发 intent
function PlayerBar() {
  const vm = useStore(selectNowPlaying);   // useSyncExternalStore，60 行
  return <Bar title={vm.title} onSeek={(t) => player.seek(t)} />;
}
```

**三条禁令**（lint 可查）：

1. 组件不许 import store 的写方法，只能 import `intent` 对象
2. 组件不许 `fetch` / `ipcRenderer`，只能调领域服务
3. 组件不许算业务（"这首歌能不能收藏"是投影的事）

收益：组件变成**纯展示 + 回调**，可以脱离整个应用单测；业务全在纯函数里，能覆盖。

## 9. 表现模型

### 9.1 合成器拥有唯一 rAF

```ts
interface Compositor {
  subscribe(fn: (t: number) => void): () => void;  // 收到同一个 t
  budget(): { usedMs: number; limitMs: number };
}
```

**规则**：全应用**只有一个** `requestAnimationFrame` 循环，在合成器里。舞台、歌词、进度条、频谱全部是订阅者。**任何模块自己起 rAF → lint 失败。**

为什么：五个 rAF 循环 = 五次时间快照 + 五次布局抖动 + 无法统一降级。一个循环的话，降级只需要"少分发几个订阅者"。

### 9.2 播放页 = 五层，按 z 收口

| 层 | 内容 | z | 可关 |
|---|---|---|---|
| **L-a 壁纸** | 纸纹理 / 图片 / 视频 / canvas | 0 | ✅ |
| **L-b 视觉** | 频谱柱 / 声纹 / 环形 / 町景（均由唯一 analyser 或对应能力供数） | 1 | ✅ |
| **L-c 封面** | 静止 / 呼吸 / 旋转 / 视差 | 2 | ❌ |
| **L-d 歌词** | 印刷 / 逐字 / 极简 / 剧场；播放页的主视觉可由当前真实歌词承载 | 3 | ✅ |
| **L-e 控件** | 顶栏 / 播放条 / 进度 | 4 | ❌ |

全局层序只有五个值：`0 1 2 3 4`（内容）、`20`（浮壳）、`40`（面板）、`50`（模态）、`60`（toast）。**禁止 `9999`。**

**控件层（L-e）的元素数量上限：7 个。** 多出来的全部进溢出菜单——这是"极简"唯一能量化的写法（否则"极简"只是形容词）。

**四套预设（参数写死，不是形容词）**：四套都遵守「歌词即时间」的语法：当前真实歌词字词是主焦点、歌词时钟是唯一推进依据、analyser 视觉只是次级反馈；预设改变环境与密度，不伪造数据。

| 预设 | L-a 壁纸 | L-b 视觉 | L-c 封面 | L-d 歌词 | 切换转场 | 成本 |
|---|---|---|---|---|---|---|
| **纸面剧场** | 冷调纸白 + 微颗粒 | 无 | 小型封面、细框 | `press`：整行一次落墨（行级 unit），无假词级动画 | 200ms `ease-out` | low |
| **夜航唱机** | 深靛夜色 + 顶部微光 | 声纹 / 环形（真 analyser） | 中型封面、细框 | `minimal`：当前句单行大字 | 320ms `ease-out` | mid |
| **极简留白** | 雾白纯底 | 无 | 无框封面 | `karaoke`：活动词焦点（真实逐字时钟） | 200ms `ease-out` | low |
| **演后余光** | 封面高斯模糊或纯紫层 | 频谱 / 町景 | 封面可见投影 | `theatrical`：上句/当前句/下句三层 | 260ms `ease-in-out` | high |

**「歌词即时间」规则**：① 首屏主焦点是当前真实歌词字/词，不能退化为封面卡片 + 普通进度条；② 逐字高亮只消费 `LyricDoc.words` 与唯一 compositor 的 `t`，有词时间时当前词放大/加重，已唱与未唱内容仍可读；③ 无逐字数据回落到行级歌词状态，不模拟打字；没有歌词就诚实显示无歌词状态；④ analyser 只画实时可得的频谱，暂停/静音/无信号时留空，不留假声纹；⑤ 颜色与字形状态必须有语义，静态截图下仍能快速识别歌名、歌词、队列与当前播放。

> 换预设不重建 store、不重新解码封面；歌词时钟与 analyser 数据源不因预设切换而重建。

### 9.3 token 是唯一颜色来源

```css
/* tokens.css —— 全项目唯一定义变量的地方。三组，谁写谁不许跨界 */
:root {

  --fs-1: 11px; --fs-2: 13px; --fs-3: 15px; --fs-4: 20px; --fs-5: 32px;
```

**规则（三条，各对应一层）**：

1. **结构层不许出现场景值**：`--ink-* / --paper-* / --accent` 的任何消费处都不能引用 `--stage-*`。UI 骨架永远不跟封面变色。
2. **取色只能写 `--stage-tint`**：采样封面中心 8×8 区，量化到 OKLCH，亮度夹在 `[0.35, 0.75]`，只被 L-a / L-b 读。
3. **材质层不许用于内容区**：玻璃只给浮壳与面板，正文区用纸色——否则整页都在"透"，阅读性崩塌。

**通用禁令**：组件里 0 个裸 hex、0 个 `!important`、字号只用 5 级（不是 12 级——**级数少才守得住**）。

### 9.4 动效只碰四个属性

`transform` / `opacity` / `clip-path` / `filter`。禁 `width/height/top/left` 动画（会触发布局）。

动效档位由主题给：`intensity: 0 | 1 | 2`。**关掉动效也必须好看**——这是设计的试金石。

### 9.5 输入纪律：谁有权响应一次按键

> 这是最容易被当成"小事"、又最容易出事故的地方：**在搜索框里打字，歌单切了**。
> 处理方式不是"记得加判断"，是**一个唯一的入口 + 一组守卫条件**。

**五个入口，只有这些**：

| 入口 | 谁消费 | 守卫条件（不满足则**静默**） |
|---|---|---|
| 全局快捷键（系统级） | 主进程 | 只在窗口失焦时生效（避免与应用内快捷键重复触发） |
| 应用快捷键 | 命令注册表 | 录键中 / 正在输入文本 / 焦点在滑杆或 `<select>` / 有模态打开 / IME 组字中 |
| 页面局部键 | 当前页面 | 同上 + 该页面处于激活态 |
| 鼠标手势（长按 / 双击 / 拖拽） | 组件 | 统一阈值：长按 **400ms**、双击间隔 **280ms** |
| 外部协议（`afeifei://`） | 主进程 | 参数白名单；单实例锁；**只在主进程解析**，渲染层只收结构化 intent |

**Esc 的优先级**（纯函数 `resolveEsc(context): Action`，可穷举单测）：

```
1. 全屏态             → 退出全屏
2. 有模态             → 关闭模态
3. 有面板（抽屉/菜单）  → 关闭最上层
4. 在详情页           → 返回上一级
5. 其它               → ignore（不吃掉，交给默认行为）
```

**为什么必须是纯函数**：Esc 是"四态以上"的典型，散在各组件里判断必然互相抢；抽成纯函数后，加一种新面板只改一个 `switch`，且能穷举测试。

**命令面板**（取 Folia 的"新功能优先命令"）：`Ctrl/Cmd + K`，结果上限 12 条，全键盘可用。新功能先进命令面板与快捷键，**按钮只留主路径**。

**隐藏交互登记册**：右键 / 双击 / 长按 / 拖拽全部登记在 `ui/interactions.md`，**不登记不许加**。理由很实在：隐藏交互是"只有作者知道"的功能，用户发现不了，测试也覆盖不到。

**验收**：输入框打 `j` 不切歌；滑杆聚焦时 `←/→` 调滑杆；Esc 在五个场景行为各异且都对；`Ctrl+K` 全键盘完成搜索 → 播放。

## 11. 安全模型

| 边界 | 规则 | 检查方式 |
|---|---|---|
| 进程 | `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true` | 启动断言 |
| 桥 | preload 只暴露**具名方法**，不暴露 `ipcRenderer`；播放状态**不进** preload | 代码审查 + 测试 |
| IPC | 每个通道校验 `sender` + 顶层 frame + 参数 schema | 伪造调用必须 reject |
| 文件 | 渲染层只见 **id**，真实路径永不出主进程；手拼路径 → 404 | 路径穿越测试（`../../`、`C:\`、UNC） |
| 协议 | 自定义协议带 **一次性令牌 + TTL**，绑 sender | 过期令牌 → 403 |
| 凭据 | `safeStorage` 加密落盘；页面永不接触明文 cookie | 反序列化测试 |
| 外链 | 只有白名单域名可 `shell.openExternal`；其他一律拒绝 | 恶意 URL 测试 |
| 用户源 | utilityProcess + host 白名单 + 超时/内存上限 | 越权脚本被拒 |

## 13. 测试模型（五层，全部进 CI）

| 层 | 覆盖什么 | 跑法 | 目标 |
|---|---|---|---|
| **纯函数** | 队列、投影、歌词解析、错误翻译、迁移器 | `node --test`（内置，零依赖） | ≥ 120 项 |

## 14. 性能预算（I5）

| # | 指标 | 目标 | 超标怎么办 | 怎么测 |
|---|---|---|---|---|
| 1 | 冷启动 → 可交互 | < 1.5s | 先出骨架，索引后台加载 | `performance.mark` 打点，5 次取中位 |
| 2 | 首帧 | < 300ms | 不挂舞台、不加载封面 | `first-contentful-paint` |
| 3 | 点播 → 出声（本地） | < 150ms | 预读下一首前 512KB | `play()` → `playing` 打点 |
| 4 | 点播 → 出声（在线） | < 800ms | 地址预取 + 失败冷却 | 同上 + 网络 mock 200ms |
| 5 | 帧率 | p95 帧间隔 < 18ms | 按序降级：关 L-b → 壁纸降为静态 → 关 C3 动效 | CDP 采 10s rAF |
| 6 | 内存（5000 首 + 舞台） | < 350MB | 缩略图 / 纹理上限 | 主进程 + 渲染进程分别采 |
| 7 | 长列表 5000 行 | p95 < 20ms | 虚拟化 | 注入数据滚到底 |

**降级顺序写死**（不许临时决定）：

```
关视觉层 → 壁纸换静态 → 歌词降为逐行（不逐字） → 频谱降为 15fps → 停节拍分析
```

**降级触发阈值（数值写死，不许"看情况"）**：

| 条件 | 动作 |
|---|---|
| 连续 **2s** 平均帧间隔 **> 20ms**（< 50fps） | 执行降级第 1 步 |
| 降一级后 **2s** 内仍 **> 20ms** | 再降一级（每次只降一级） |
| 连续 **5s** 平均 **< 14ms**（> 70fps） | 回升一级（每次只升一级，防抖动） |
| 用户手动锁定画质 | 关闭自动降级，只在控制台记警告 |

> **18ms 与 20ms 是两个数，不是笔误**：18ms 是"合格线"（预算），20ms 是"动作线"（降级）。中间 2ms 是**迟滞**——否则在阈值边缘会反复升降，看起来像界面在抽搐。

**预算进 CI**：先进 #1 与 #5（最稳），其余人工。**没有测法的预算等于没有预算。**

## 15. 为什么不是 XXX（把被否掉的选项写下来）

| 选项 | 为什么不选 | 什么情况下才选 |
|---|---|---|
| **Tauri** | 视觉与音频都靠 Chromium：Web Audio 的 AnalyserNode 是可视化与节拍的基础，Rust 侧解码就拿不到；且 macOS/Linux 用 WebKit，WebGL2/`backdrop-filter`/`dialog` 支持参差。它省的是包体与内存，**不减渲染成本** | 包体与内存成为用户拒绝理由，且频谱改由 Rust 侧输出 |
| **Electron + `nodeIntegration: true`** | 渲染层拿到 `require` 等于把文件系统交给网页 | 永不 |
| **Redux / Zustand / MobX** | 它们解决"状态怎么组织"，不解决"谁有权改"。60 行 `useSyncExternalStore` 已经够，而且**单写者**得靠 lint 和目录结构守，不是靠库 | 状态规模超过一个域 200 个字段时再谈 |
| **React Router** | 单窗口应用，路由是**状态**不是 URL。引入 router 会让"页面"和"状态"两套真相并存 | 要做网页版时 |
| **SQLite** | 需要 native 依赖（ABI 匹配、打包体积、升级风险）；5 万首以内 JSON+WAL 够用 | 曲库 > 10 万首，或需要复杂查询/全文检索 |
| **Canvas 渲染整个 UI** | 文本排版、输入法、无障碍、选中、滚动全部要重造。**这四条是浏览器送你的，别丢** | 永不（除播放页的视觉层） |
| **WebGL 做 2D 界面** | 同样的排版问题，且首帧成本高 | 永不 |
| **插件市场 / 通用脚本钩子** | 扩展点每多一个，故障面多一片；通用钩子等于放弃契约 | 四个扩展点被证明不够时 |
| **服务端渲染 / 网页版** | 桌面定位；云服务会触发 AGPL 的网络条款义务 | 明确要做多端时 |

- [ ] 两家音源，真号全链路；失败两层（通用码 + 平台翻译）

- [ ] 单测：错误翻译 ≥ 20 项、歌词解析 ≥ 30 项

### M4 · 表现（能换看法）
