## 2026-11-03 · 扫码"没反应"真因：check 的 key 没传到本地服务

- **commit**：见本条
- **动机**：用户"扫完码后没有反应"——二维码出来了、也扫了，但弹层永远停在等待。
- **根因**：`/login/qr/check?key=` **必须带 key**，而 key 停在渲染层（LoginDialog 的 session.key），`qq:poll` 的 IPC 链路没把它传下去——check 空转永远 801。读包内 `qrCheckOperation.js` 才确认：成功时 **code 803 + 会话写进响应 cookie**（与网易云 801/802/803 完全同款语义），key 是必填。
- **修法**（key 贯通四层）：`LoginDialog` 的 key → `pollLogin("qq")` → `api.qqPoll(key)` → `qq:poll` handler → `callQq("qrPoll", {key})` → `/login/qr/check?key=`。check 成功后包自动把会话写进响应 cookie（fetchJson 默认 session 自动存），`/login/status` 随即非空 → loggedIn。
- **顺手修**：包返回的英文状态文案（"Waiting for QR scan"）翻译成人话（"等待扫码"/"已扫码，请在手机上确认"）——00 §10 状态与错误同权。
- **坑**：IPC 参数在渲染层有、主进程丢——**跨进程传参要在 handler 签名里显式接**，只看 invoke 调用方以为"参数自然会在"是错觉。这次是 key，之前是 scheme 的冷启动 pending，同一类病：**跨边界的每个参数都要有明确的搬运记录**。
- **验证**：verify ALL GREEN。等你重新扫码确认闭环。

## 2026-11-03 · 扫码"没反应"第二层真因：startLogin 丢真实 unikey + 扫码 App 不对

- **commit**：见本条
- **动机**：用户再报「扫码了没反应」。日志还原：check 返回 800（不是 801/802/803），但 cookie 又确实到了、换凭证被上游拒（50006）。
- **根因**（两个叠加）：
  1. **UI 盲区（我们自己的 bug）**：`bootstrap.startLogin` 把真实 unikey 丢了，写死返回 `key: "qq"`——弹层轮询永远拿字面量当 key，`sessionFor` 404 → check 800 → 弹层第一次轮询就停，二维码成死图。preload/services 的 `qqLogin` 返回类型也跟着把 key 丢了（同一处断点在三处显形）。
  2. **登录失败（用户侧动作 + 包语义）**：真实二维码的 MQTT 监听还活着，用户的扫码确认事件其实到了本地服务，但包向上游换凭证被拒（`50006` = `login.wrong-scan-app`）——channel=qq 的码必须用**手机 QQ** 扫，用 QQ 音乐 App 扫（或 App 绑微信）就是这条失败。
- **修法**：① key 带真实 unikey + `qq:` 前缀贯通（preload/services 类型同步）；② `qq:poll` 把包的 `failureHint` 按文案 key 翻成中文透出（wrong-scan-app / device-limit / rate-limited 等七条）；③ pollLogin 翻译 800；④ 弹层扫码提示写明「手机 QQ，不是 QQ 音乐 App」。
- **坑**：**key 的分流前缀与真实值是两个东西**——上次「key 贯通」只修了 IPC 链路，渲染层入口还在丢。跨层传参每一跳都要核对类型签名，类型系统这次实际拦住了 preload 的丢字段（TS2339），但拦不住 bootstrap 里写死的字符串。
- **遗留**：包对 50006 的说明是「手机 QQ 扫码也实测见过，原因未知」——若用手机 QQ 仍失败，下一步是加 channel=qqmusic（QQ 音乐 App 扫码通道，包已支持，我们未接）。失败后 15s 内点「刷新」会撞包的 429 冷却，提示还是英文，待翻。

## 2026-11-03 · QQ 登录真机首跑两连修：http 白名单 + qrimg 字段

- **commit**：见本条
- **动机**：用户真机手点 QQ 登录——二维码弹层报 `qq:login: 只允许 https: http:` 且无图。
- **根因**（两个叠加）：
  1. `fetchJson.validate` 只放行 https——QQ 后端是**本机 `http://127.0.0.1:3210`**，全部请求被协议白名单拦下。修：放行 `http:` 的 127.0.0.1/localhost（本机回环），对外仍强制 https。
  2. `qqQrStart` 的 `qrImage` 返回的是**猜的端点路径**，而包实际返回 `data.qrimg` = 完整 PNG dataURL。之前实测"qrimg 为空"是探针读错字段名（读成了 qrImage/image）——**字段名 `qrimg` 一直有值**。修：读真实字段，空则抛人话错误。
- **坑**：两次教训同源——①协议白名单写死 https 时没想过"本机回环"这个合法场景；②探测脚本自己的字段名猜错，把"有数据"误判成"没数据"。探针报告的字段名要与上游实测对照，不能只信自己的取法。
- **验证**：verify ALL GREEN；`/login/qr/create`（qq/wechat 通道）实测返回完整 PNG dataURL；`check` 801 语义正常。扫码登录的最终确认仍需你手点。

## 2026-11-03 · QQ 登录改"应用内二维码"（b80b6be，后被 P1 换包方案接替）

- **commit**：`b80b6be`
- **动机**：用户否掉弹网页方案（"你看看 Folia 的登录怎么做的"）。核查 Folia（`api/qq.js`，本机网络拉不到 raw，经仓库结构确认）：**它的 QQ 登录是自建服务端做的**（`QQ_SESSION_SECRET`，桌面端只调自家 API）——没有本地实现可抄；能抄的是它的**体验**：应用内二维码 + 轮询。
- **为什么不能手写 ptlogin 协议**：实测三连拒——node fetch、Electron `net.fetch`（Chromium 栈、正确 Referer）全部 403/不发 qrsig。QQ 风控拦的是**一切手写 HTTP 请求**，不是某个客户端。
- **方案**：隐藏 BrowserWindow 载入 **QQ 自己的 xlogin 登录页**——协议、轮询、二维码刷新全由页面自己做（它就是真浏览器，风控无感）。主进程只做两件事：`executeJavaScript` 提取页面上的二维码 `<img src>`（渲染层 `<img>` 直接加载，session 自动带 qrsig）与页面状态文案透传；登录成功判定仍是 `qm_keyst`/`uin` cookie 写入。
- **改了**：`qqSession.ts` 重写（startQrLogin/pollQrLogin）、IPC（qq:login→qq:poll）、`LoginDialog`（props 加 `scanHint`、poll 支持二维码更新、手机号 tab 按 `sendCaptcha` 存在性渲染——QQ 源只有扫码 tab）、`OnlineView`（两源统一走 LoginDialog，start/poll 按 key 前缀分流）。
- **关键决策**：**"谁渲染二维码"不再是我们**——QQ 页面自己刷新过期的二维码，我们每次 poll 顺手提取最新的给 UI。手写协议 = 永远追着风控跑；承载页面 = 风控跟我们无关。
- **坑**：
  1. `web_fetch`/node/jsDelivr 到 GitHub raw 全被重置——Folia 的 qq.js 没拿到，靠仓库结构 + README 确认了它的服务端架构就足够决策了。
  2. ptlogin 页面的 DOM 结构没有官方保证，提取用了三重 fallback selector——QQ 改版时二维码提取会失败（表现：应用内一直"正在获取二维码"），修法就是更新 selector。
- **遗留**：本条方案仍是可用回退（见 `b80b6be` 历史）；按 `docs/05` P1 应换 `@yakult-green-tea/qq-music-api` 包。

## 2026-11-02 · 冒烟位置断言改为轮询（第二次「检查太早」）

- **commit**：`bd2f20a`

### 改了什么

| 位置 | 做了什么 |
|---|---|
| `main/net/fetchJson.ts` | `net.fetch` + 超时 + https 校验 + Set-Cookie 透出 |
| `main/net/cookie.ts` | 写 session cookie（基础 cookie `os=pc` / `appver=8.10.90`） |
