## 2026-11-02 · 冒烟位置断言改为轮询（第二次「检查太早」）

- **commit**：`bd2f20a`
- **现象**：`npm run verify` 报 `位置应恢复成 2000±1000ms，实际 0`。
- **原因**：功能没坏，是**测试读得太早**。`cue` 之后引擎还要 `load` 才会 `seek`，只读一次必然撞上还没锚定的 0。
- **修法**：断言改成轮询等待（8s 上限）。**判据没有放宽**，仍是 2000±1000ms；改的是"等它到"而不是"立刻读"。

- **这是第二次踩同一个坑**：

| 次数 | 场景 | 表现 |
|---|---|---|
| 第一次 | M1 查 `h1` | React 还没渲染完，DOM 为空 |
| 第二次 | 本次查进度条 | store 已恢复，引擎还没 seek |

  两次的共同点：**状态已就绪，但 DOM 还没反映出来**。

- **结论（写进习惯）**：以后所有 DOM 断言默认轮询，除非能证明那一处是同步渲染的。直接读一次只在"刚由我触发且同步生效"时成立。

- **遗留**：`waitFor` 的超时值（8s）是拍的。启动慢的机器上若仍偶发失败，应改成"先等 `.status` 脱离 loading，再读位置"这种**按状态等**而不是按时间等。

## 2026-11-02 · 网易云适配器 + 扫码登录 + 在线播放

- **commit**：`6e41891`
- **动机**：用户「我用网易云扫码」。M3 的第一家真音源。

### 接口实测（先验后写，不靠记忆）

用 node 直接打官方接口，结果决定了后面所有实现：

| 接口 | 匿名实测 | 结论 |
|---|---|---|
| `POST /api/cloudsearch/pc` | 200，3 首周杰伦 | 搜索匿名可用 |
| `GET /api/song/lyric` | 200，lrc 704 字节 | 歌词匿名可用 |
| `POST /api/login/qrcode/unikey` | 200，返回 unikey | 扫码可用 |
| `GET /api/song/enhance/player/url/v1` | **data[0].code = -110，url 为 null** | **匿名拿不到地址，必须登录** |

### 改了什么

| 位置 | 做了什么 |
|---|---|
| `main/net/fetchJson.ts` | `net.fetch` + 超时 + https 校验 + Set-Cookie 透出 |
| `main/net/cookie.ts` | 写 session cookie（基础 cookie `os=pc` / `appver=8.10.90`） |
| `main/util/qrcode.ts` | 文本 → 二维码 dataURL |
| `capability/sources/netease/` | `search` / `getDetail` / `getUrl` / `getLyric` / `login` + 扫码三件套 |
| `ui/views/online/LoginDialog.tsx` | 扫码弹层，`setTimeout` 链式轮询 |
| `capability/audio/engine.ts` | `resolveSrc`：本地走 appmedia 令牌，`https://` 直链直接用 |
| `renderer/index.html` | CSP 放开 `media-src https:` 与 `img-src https:` |

- **关键决策**：
  1. **不自己实现 CookieJar**。`net.fetch` 走 Chromium 网络栈，扫码成功后的 `Set-Cookie` 自动进 session，后续请求天然带登录态。旧仓库手写了 CookieJar，这里是**少写一层**。
  2. **拿不到地址必须区分「未登录」与「无版权」**。混成一句"没版权"，用户会以为歌下架了，然后去搜别的版本——真正的原因是没登录。现在是：未登录 → `auth-required`（请先登录），已登录才 → `track-missing`。
  3. **二维码放主进程**。`qrcode` 只在扫码那一下用得到，进渲染 bundle 等于让每次启动都加载它。
  4. **登录态缓存 30s**。界面会逐首取地址，每首都查一次账号接口不划算；但网络出错时**不谎报已登录**（旧仓库踩过，界面会显示假用户名）。

- **坑**：
  1. **`-110` 这个码的含义不是"无版权"**，而是"没有可用地址"，最常见原因是未登录。按字面理解会写出错误的用户提示。
  2. Chromium **不允许手动设置 `Cookie` 请求头**（会被忽略）。基础 cookie 只能通过 `session.cookies.set` 写，不能塞进 headers。
  3. 旧仓库的网络层有 `CookieJar` 类，看起来"参考价值高"，但在 Electron 里是多余的——**照抄会让代码多一层且更容易出错**。

- **验证**：`npm run verify` ALL GREEN —— 54 个源文件、lint 6 条、212 项测试、冒烟（2 个音源已注册）、3 条性能预算。真网接口用 node 直连验证（不进 verify，避免网络波动导致红灯）。

- **遗留**：
  1. **扫码登录未经人工验证**：需要你在应用里点一次（流程已实现，接口已通）。
  2. **在线播放未经真号验证**：地址要登录后才拿得到。
  3. 在线曲目没有标题：`trackId` 直接是 URL，播放条显示 URL 尾巴。应给 store 加 `trackTitle`（M4）。
  4. 会员音质（flac）没声明；`qualities` 只到 320k。
  5. 歌单 / 专辑 / 电台（`canGetPlaylist` 等四项）都声明为 false —— 契约支持，实现没做。

## 2026-11-02 · 歌词四格式解析 + 在线页（M3 可离线部分完成）

- **commit**：`226c92d`
- **动机**：M3 剩下的部分里，歌词与音源切换**不需要真号**，先做透；真音源只剩"填适配器"。

### 一、歌词（`capability/lyrics/`）

| 文件 | 做了什么 |
|---|---|
| `detect.ts` | 格式识别：**先看结构标记再看时间轴长相** |
| `parse.ts` | LRC / 增强 LRC / QRC / YRC / TTML / 纯文本 → 统一 `LyricDoc`（毫秒） |
| `reflow.ts` | 智能重排：行首不留标点、尾行不留单字、时间按字数分配 |

- **关键决策**：
  1. **TTML 用正则解，不用 XML parser**。解析要能在**主进程**（无 `DOMParser`）和 **node 测试**里跑。TTML 歌词的结构就 `p` / `span` 两种标签。
  2. **时间一律毫秒**，与 `clock` 同单位。少一次单位换算就少一次换错的机会。
  3. **逐字行不参与重排**：切了逐字时间就对不上。重排是给"整行显示"用的。
  4. **解析失败回落纯文本**，绝不给界面一个空对象。

- **坑**：
  1. **QRC 会被误判成 LRC**，如果只看"有没有 `[mm:ss]`"。它的行首是 `[毫秒,时长]`、**没有冒号**，所以识别顺序必须先看结构标记。
  2. **增强 LRC 的尖括号时间指的是"接下来那段"的起点**，第一段文本从行时间开始。第一版测试断言写成 17200，实际 16800 —— **实现是对的，测试写错了**。
  3. 旧仓库样本是**秒**，新契约是**毫秒**。搬样本不换算，断言会整体差 1000 倍。

### 二、在线页

| 文件 | 做了什么 |
|---|---|
| `ui/views/online/` | 音源下拉（来自注册表）+ 搜索 + 结果表 |
| `ui/index.tsx` | 本地 / 在线 tab |
| `ui/bootstrap.ts` | `registerProvider(demoProvider)` + `sources()` / `searchOnline()` / `resolveOnlineUrl()`，错误统一 `humanize()` |

- **关键决策**：**音源下拉不写死，读注册表**。加第三家源时下拉框自动多一项 —— 这是 `docs/01` §2.4"加一个同类只动两处"的兑现。
- **坑**：demo 源原本抛 `new Error("capability-missing: …")`，界面显示成"出了点问题"。**错误必须结构化带 `code`**，靠 message 猜是错的。两边都修：demo 抛 `Object.assign(new Error(...), { code })`，`translateError` 加 message 兜底（第三方源常见这种写法）。
- **验证**：冒烟新增完整链路——切在线 tab → 读注册表选项 → 搜索 → 点第一条 → 断言提示是**中文人话**且**不含错误码/异常原文**。实测输出"当前音源不支持这个操作"。

- **验证**：`npm run verify` ALL GREEN —— 49 个源文件、lint 6 条、**212 项测试**、三阶段冒烟（含在线链路）、3 条性能预算。

- **遗留**：
  1. **在线播放没接**：demo 不提供地址。真音源接入时要开 CSP `media-src https:` 并给 engine 加 `loadRemote(url)`，现在**故意不提前放开**。
  2. 两家真音源（网易云 / QQ）仍未接，需要真号联调。
  3. EQ / ReplayGain（M3 第 9 步）没做。
  4. 歌词还没接进 UI：拿得到 `LyricDoc`，但播放页还没显示，属 M4 表现层。

## 2026-11-02 · M2 曲库完成（5000 首不卡）

- **commit**：`9596527`
- **动机**：按 `docs/01` §4 M2 施工单，做到"5000 首不卡"。
- **改了**：

| 位置 | 做了什么 |
|---|---|
| `domain/library/schema.ts` | Track 形状、路径规范化（身份走小写、显示走原样）、迁移器（v1 校验 + 去重 + 过滤坏记录） |
| `domain/library/index-store.ts` | 快照 + 增量日志的 `replay`/`parseLog`/`diffPaths`；`findMissing` 只标记不删条目 |
| `domain/library/scan.ts` | 批量 stat → 只对新增/变化的读标签 → 压缩成新快照；`restoreLibrary` 走快照+日志回放 |
| `domain/library/state.ts` | 曲库自己的 store（与播放 store 分开），唯一写入口 `setTracks`/`setQuery` |
| `domain/search/` | 拼音首字母搜索（21KB 表）+ 打分（字段开头命中优先） |
| `domain/library/dedupe.ts` | 两档去重建议，只出建议不自动删 |
| `projection/library.ts` | `selectVisible` / `scrollTopFor` 虚拟列表窗口 |
| `main/fs/` | `readTags`（8 路并发）、`statFiles`、`indexFile`（原子写 + 日志追加） |
| `ui/views/library/` | 曲库页：搜索 + 虚拟滚动 + 缺失态 |
| `scripts/perf.mjs` | 3 条预算：二次启动恢复、滚动帧间隔、搜索响应 |

- **关键决策**：
  1. **曲库不进 kernel store**。播放状态要"每次变化通知所有订阅者"，曲库只需要"列表变了/搜索词变了"两个通知；5000 条塞进去会让每次 dispatch 都白算一遍。
  2. **身份用规范化路径的小写，显示用原始路径**。Windows 大小写不敏感，不做统一就会出现 `C:\A.mp3` 与 `c:\a.mp3` 两首歌。
  3. **增量靠 stat 比对**，不靠全量重读标签。5000 首改 3 首就只解析 3 首——这是"二次扫描也不慢"的全部意义。
  4. **拼音只取首字母**。完整拼音表 103KB 只为了"全拼搜索"这种没人用的输入方式，首字母 21KB 就够"打 2 个字母出歌"。
  5. **缺失只标记不删**。自动移除会让用户以为歌被吞了；外接硬盘没插时更是灾难。

- **坑**：
  1. **`setTracks` 里把通知参数传成 `false`**，曲库加载完界面永远显示"0 首"。这不是"少通知一次"，是"完全不通知"。这类漏通知只有端到端能发现——单测里我调 `getFiltered()` 拿得到数据，所以全绿。
  2. **`readTags` 串行解析，5000 首外推 37.3s，超 30s 预算**。改 8 路并发后 80 个文件从 597ms 降到 82ms（7.3 倍），外推 5.1s。**预算不是写完代码才想的事，是 perf 脚本逼出来的。**
  3. **lint 规则 6 把字符串字面量里的 `library` 也当业务词**，`main/fs/indexFile.ts` 里写 `"library.json"` 就报错。修法是判定前先剥掉字符串——**规则误伤会让人直接关掉规则**。
  4. 路径规范化必须两边一致：扫描时用原始路径、比对时用小写，混了就出现"明明扫到了却算缺失"。

- **验证**：
  - `npm run verify` **ALL GREEN**：34 个源文件、lint 6 条、**132 项纯函数测试**、build、三阶段冒烟、3 条性能预算
  - 二次启动恢复 5000 首：**24.3ms**（预算 120ms）
  - 5000 行滚动帧间隔 p95：**6.8ms**（预算 20ms），虚拟列表只渲染约 30 行
  - 搜索响应：**11.9ms**（预算 100ms）
  - 真扫描 `C:\Windows\Media`：80 个音频，列目录 8ms、解析 79ms（外推 5000 首 ≈ 5.1s）
  - M2 测试下限：索引 27 ≥ 15、去重 10 ≥ 5（累计 132）

- **遗留**：
  1. **"点扫描按钮 → 选目录 → 入库"这条端到端路径没自动化**：`dialog.showOpenDialog` 拦不住。IPC 链路（scan/statFiles/readTags）已在 perf 里验，编排由单测覆盖，但"真的点一次"仍要人工。
  2. 首次扫描 5000 首是**外推值**，没在有 5000 个真音频的机器上跑过。
  3. 封面缩略图（M2 第 5 步）没做：`hasCover` 标了，但没生成缩略图、没做 LRU。列表暂时不显示封面。
  4. 收藏/歌单/历史（"顺序外"三节）没做，等索引稳定后插入。
  5. 搜索是 O(n) `includes`，5000 条实测 11.9ms 够用；10 万首才需要索引化。
  6. 曲库没有排序 UI（按扫描顺序），也没有"正在播的高亮"。

- **关键决策**：
  1. **clock 不碰 DOM**。环 0 不许碰 DOM，所以时钟不直接读 `audio.currentTime`，改由 capability 用 `attach(() => audio.currentTime * 1000)` 注入。于是"谁读 currentTime"有了唯一答案：engine。
  2. **状态机做成纯函数表**而不是散在事件回调里。六个状态 × 七个事件的转移一次写完，能穷举测；未定义的转移一律保持原状态（宁可没反应，也不要把界面打成 error）。
  3. **实时位置不进 store**。store 的 `positionMs` 只记"用户最后一次 seek / 切歌的位置"，进度条每帧从 `clock.t()` 取 —— 否则每帧一次全量通知 + 整棵树重渲染。
  4. **界面用 `app://` 而不是 `file://`**。见坑 1，这不是洁癖，是能否显示的问题。
  5. **3 秒规则留在 kernel**，但由 UI 把 `atPositionMs` 带上来 —— 规则不散到 UI，store 也不必追实时位置。

- **坑**：
  1. **`file://` 下 CSP 的 `'self'` 匹配不到任何 URL**，`<script src>` 被静默拦掉，窗口一片空白且控制台没有明显报错。**M0 那条"窗口显示 afeifei"其实从未被验证过**（当时只看了进程存活和日志）。改用 `app://` 自定义协议后才真正跑起来。推论：**判据必须验到 DOM，不能只看进程活着。**
  2. **`protocol.registerSchemesAsPrivileged` 多次调用会互相覆盖**，不是累加。我原本 `app` 和 `appmedia` 各调一次，后一次把 `app` 的 `standard/secure` 抹掉了 —— 症状是 HTML 能加载、`<script>` 却被拦。必须一次性传数组。
  3. **`file://` 下 ES module 会被 CORS 拦**，renderer 产物必须是 `iife` + 普通 `<script>`。
  4. **`beforeunload` 的 flush 会覆盖测试注入的存档**。想验"重启恢复"必须 `SIGKILL`（模拟断电），不能靠 reload —— 否则测的是"退出时保存"，不是"崩溃后恢复"。
  5. **冒烟第一次失败是"查得太早"**：页面刚加载就查 `h1`，React 还没渲染。所有 DOM 断言都要轮询等待，不能查一次就下结论。
  6. **`main/renderer/` 这个目录名和环 4 撞了**，lint 规则 6 因此误报。两者都改了：目录改名 `main/host/`，规则改成按解析后的真实路径判断而不是字符串匹配。

- **验证**：
  - `npm run verify` **ALL GREEN**：22 个源文件、lint 6 条无违规、**69 项纯函数测试**、build、smoke
  - 冒烟实测：`Alarm01.wav` 解码 5.57s、`currentTime` 推进；无效令牌返回 410；**SIGKILL 后重启，曲目 / 位置 2000±1000ms / 音量 30% / 暂停态 全部恢复**
  - M1 测试下限：queue 29 ≥ 20、clock 14 ≥ 10、累计 69 ≥ 30

- **遗留**：
  1. **"切歌不闪白"仍未验证**：白屏要靠截图对比，冒烟只能证明 DOM 与状态一致（`4d114ed` 补上了连切 20 首与淡入淡出）。
  2. **`player/cue` 的时钟锚点 bug 是冒烟抓到的**（修在 `58a8834`）。说明"恢复后进度条从 0 开始"这类问题只有端到端能发现，纯函数测试测不到装配层。
  3. store 仍是全量快照订阅，5000 条时需 selector 级订阅（M2）。
  4. `ui/compositor.ts` 是最小版，只分发 `now`；M4 才接 `clock.t` 的统一分发与降级。
  5. 切歌的淡入淡出是写死的 8ms/20ms，且只覆盖"换曲"；暂停/恢复的淡出与可配置 crossfade 属 M3 的 fade stage。
  6. **M0 判据第 1 条需要重写**：`docs/01` §2.6 写的是"窗口里显示 afeifei"，但当时的验证方式（进程存活 + 日志）根本证明不了它，实际是空白的。已回写。
