# 15 · 交付门槛：95 分

> **由来**：2026-11-03，用户在看到"6 套播放样式里 5 套没过 95 就直接摆出来"之后立的规矩——
> **"之后设计开发必须自评过 95 分才能输出。"**
> **效力**：与 `00` 的不变式同级，**不是建议**。`.codebuddy/rules/95-gate.mdc` 是它的执行版本（`alwaysApply: true`）。

---

## 1. 为什么要立这条

不是洁癖，是因为**"先给你看看"的成本全落在用户身上**：

| 我们以为 | 实际发生 |
|---|---|
| "先出个方向，用户选一个" | 用户要在**5 个半成品**里挑，比没有更累 |
| "能跑就行，细节后面补" | 细节永远补不上，因为下一轮又在赶新东西 |
| "我评了 92，挺高了" | 92 分的作品看起来"差一点"，但差的正是决定性那一点 |

**一个 96 分的作品 > 六个 90 分的作品。** 这条规则就是把这句话变成硬约束。

---

## 2. 两条评分尺（设计 / 开发）

### 2.1 设计（100）

| 维度 | 权重 | 扣分口径 |
|---|---|---|
> **2026-11-03 换尺**：用户给了专业评审标准，**下面是唯一有效的设计尺**。此前用的"辨识度/惊艳/完成度/品类/可实施/一致"六维尺**作废**（它把"我觉得惊艳"当维度，专业度不够）。

| 一级维度 | 分值 | 核心考察 |
|---|---|---|
| **创意与概念** | 25 | 原创性、思想深度、概念与目标契合度 |
| **视觉表现** | 25 | 色彩、版式、构图、视觉层次（至少 3 级信息层级） |
| **功能与传达** | 20 | 信息效率、认知成本、是否达成设计目标 |
| **执行与工艺** | 20 | 像素级精度、技术规范、素材质量、可交付性 |
| **一致性与适配性** | 10 | 风格统一、品牌匹配、多场景适配、可扩展 |

**四档口径**（每维都要落到档，再取分）：

| 档 | 创意 | 视觉 | 功能 | 执行 | 一致 |
|---|---|---|---|---|---|
| 优秀 | 21–25 | 21–25 | 17–20 | 17–20 | 9–10 |
| 良好 | 16–20 | 16–20 | 13–16 | 13–16 | 7–8 |
| 一般 | 11–15 | 11–15 | 9–12 | 9–12 | 5–6 |
| 较差 | 0–10 | 0–10 | 0–8 | 0–8 | 0–4 |

**等级线**：90–100 **A+ 卓越**（行业顶尖、可作标杆）｜80–89 A 优秀｜70–79 B 良好｜60–69 C 合格｜50–59 D 待改进｜0–49 F 不合格。

**95 分落在 A+ 区间**——意味着"创意与执行俱佳的标杆作品"，不是"能看"。这就是这条闸门的真实标高。

**两条使用纪律**（来自标准原文）：
1. **分项打分再求和**，不许凭整体印象直接给总分；
2. **客观优先**——能用"层级是否清晰、有没有错位、信息能否 3 秒读到"这类可量化判据，就不许用"我觉得好看"。

### 2.2 开发（100）

| 维度 | 权重 | 扣分口径 |
|---|---|---|
| **功能正确** | 25 | 判据逐条过；边界（空/满/超长/断网/并发）有覆盖 |
| **不变式** | 20 | I1–I5、lint 7 条、五环依赖、单写者；破一条直接 0 分 |
| **判据可红** | 20 | 每条判据能写成测试或脚本，且**先红后绿**；"能跑"不算判据 |
| **回归安全** | 15 | smoke / perf / `*-shots` 三处选择器已查；没查扣满 |
| **规模与可读** | 10 | 一提交 ≤400 行；文件 ≤400 行；TODO 零新增 |
| **诚实** | 10 | 没做的写进"遗留"；不编数据（拿不到就显示 `—`）；不把估算写成实测 |

## 3. 输出格式（缺一项就不算交付）

```
## 自评：xx / 100

| 维度 | 分 | 扣分理由（具体到哪一处） |
|---|---|---|
| … | … | … |

### 迭代记录
v1 xx → 扣分点 A/B/C → 修法 → v2 yy → 仍扣 D/E

### 证据
- 设计：截图路径（改前 / 改后）
- 开发：命令与真实输出（lint / tsc / 测试）
- 测试：只列**本次 diff 触及的功能路径**的验证结果（见 3.1）
```

---

## 3.1 测试范围（2026-11-04 用户定）

**只测你新增或改动的功能。** 其他不挨边的功能不测试——全量回归纯浪费时间，不加分。

| 情形 | 测什么 |
|---|---|
| 本次改动 | 逐条验证可红可绿的判据，先红后绿 |
| 没被 diff 触及的功能 | **不跑、不重测、不在交付说明里写"已验证"** |
| 改了公共函数/共享模块 | 只测被影响的那几个调用点，并说明为什么要测 |
| 改了 kernel/clock/store 等不变式代码 | 按 `docs/00` 的不变式只测对应项 |

交付说明里写测试结论时，**只列本次新功能的验证结果，不冒充全量验证**。执行版本：`.codebuddy/rules/testing-scope.mdc`（`alwaysApply: true`）。

## 4. 假自评黑名单

| 假自评 | 识别方法 |
|---|---|
| 把"能跑"当"完成" | 问一句：空态长什么样？错误态呢？窄窗呢？ |
| 把"布局变体"当"多个设计" | 把两版并排，如果信息结构一样只是骨架不同 → 算一个 |
| 无扣分项 | 96 分以上的作品也该有 4 分可扣；写不出 = 没评 |
| 分数无理由上涨 | 对比上一版的扣分项，逐条核对是否真的修掉 |
| 拿旧截图当新证据 | 查文件修改时间与截图内的时间码 |
| 只做 happy path | 数一数实现了几个状态：正常 / 空 / 错 / 加载 / 降级 |

---

## 4.1 评分前置条件：**必须先真实渲染，再打分**（2026-11-03 血的教训）

我给六套样式打过 96/97，用户贴出真机截图后实测只有 58–84。根因三条，全部写进流程：

1. **合成器滞后**：DOM 切换了、画面还停在上一条 → `scripts/mockup-shots.mjs` 必须**回读 `.view.on`** 并**等两帧 + 260ms** 再截。不校验就截 = 假证据（我因此把「影院」截成了「剧本」）。
2. **CSS 渐变不能当封面**：图为主的设计（影院/海报/碟）在占位渐变下必然崩。必须拿**真实照片**验（本机 `C:\Windows\Web\Wallpaper\Windows\img0.jpg` 即可）。
3. **对比度不能靠"设计软件里的感觉"**：`hair .09` / `mute .28` / 未播 `.18` 在 1334×747 真屏上等于隐形，所有"细节设计"都白做。统一提到 `.16 / .46 / .30` 再评。

**所以：任何设计稿的自评，必须附 `docs/assets/mockups/*.png` 的真实截图路径；没有截图 = 不许评分 = 不许输出。**

## 5. 例外

只有一种：用户**明确要求**"先看草稿/先定方向"。此时输出**第一行**必须写：

> **未达 95（xx 分）：草稿，仅用于确认方向，未做空态/边界。**

例外不许变成常态。**同一话题连续两次用例外，就是没把这条规则当回事。**

## 7. 反面案例（别重犯）

**2026-11-03**：一次输出 6 套播放样式，自评 96 / 92 / 90 / 93 / 94 / 91。
- 违规 1：五套没到 95 就输出；
- 违规 2：其中四套是"换骨架"，不算四个设计；
- 违规 3：为了让数量好看，把"布局变体"当成了"设计多样性"；
- 用户反馈：**"你设计了毛线 6 个，你用心设计了吗？自评到 95 分以上了吗？"**

**正确做法**：只交 96 那套；其余留着自己迭代（补空态、补降级、补窄窗、补键盘），达标一个交一个。
